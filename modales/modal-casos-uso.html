¿Qué es un diagrama de casos de uso?

Un diagrama de casos de uso es una representación gráfica de las interacciones entre los actores (usuarios o sistemas externos) y el sistema, mostrando las funcionalidades que ofrece.

🏗️ Elementos principales de un diagrama de casos de uso:

👤 Actor:
  ✓ Representa un rol que interactúa con el sistema
  ✓ Puede ser una persona (ej: Secretaria, Dentista, Cliente)
  ✓ Puede ser otro sistema (ej: Sistema de pagos, API externa)
  ✓ Se dibuja como un "muñeco" o con el estereotipo <<actor>>

⭕ Caso de uso:
  ✓ Representa una funcionalidad específica del sistema
  ✓ Nombre en verbo + sustantivo (ej: "Registrar paciente", "Procesar pago")
  ✓ Se dibuja como una elipse u óvalo
  ✓ Describe una secuencia de acciones que produce un resultado valioso

📦 Límite del sistema:
  ✓ Rectángulo que delimita el alcance del sistema
  ✓ Los casos de uso van dentro del rectángulo
  ✓ Los actores van fuera del rectángulo

➡️ Relaciones:
  ✓ Asociación: entre actor y caso de uso (línea sólida)
  ✓ Include: relación obligatoria entre casos de uso (---<<include>>---)
  ✓ Extend: relación opcional entre casos de uso (---<<extend>>---)
  ✓ Generalización: herencia entre actores o casos de uso

📌 Ejemplo práctico:

En un sistema de clínica dental:

  • Actores: Secretaria, Dentista, Paciente, Administrador
  • Casos de uso: "Registrar paciente", "Agendar cita", "Registrar tratamiento", "Generar factura", "Procesar pago"

Relaciones entre casos de uso: «include» y «extend»

Include (Incluye)

Características:

  • ✓ Relación obligatoria entre casos de uso
  • ✓ El caso base siempre ejecuta al caso incluido
  • ✓ Se usa para reutilizar comportamiento común
  • ✓ Ayuda a evitar duplicación de descripciones
  • ✓ Se representa con una flecha punteada con la palabra <<include>>

📌 Ejemplo:
"Hacer compra" <<include>> "Procesar pago"
→ No puedes comprar sin pagar, es obligatorio.

Extend (Extiende)

Características:

  • ✓ Relación opcional entre casos de uso
  • ✓ El caso extendido se ejecuta solo bajo ciertas condiciones
  • ✓ Se usa para comportamiento condicional o excepcional
  • ✓ El caso base no depende del extendido
  • ✓ Se representa con una flecha punteada con la palabra <<extend>>

📌 Ejemplo:
"Aplicar descuento" <<extend>> "Hacer compra"
→ Solo se aplica si el cliente tiene un cupón de descuento.

📊 Diferencia clave:

Include: "Siempre ocurre" → Relación de uso obligatorio
Extend: "A veces ocurre" → Relación de extensión condicional

🎯 Include se usa para factorizar comportamiento común.
🎯 Extend se usa para añadir comportamiento opcional.

📌 Más ejemplos:

  • Include: "Registrar usuario" <<include>> "Validar correo electrónico" (siempre se valida)
  • Extend: "Enviar notificación" <<extend>> "Registrar cita" (solo si el paciente activó notificaciones)
  • Include: "Iniciar sesión" <<include>> "Verificar credenciales" (siempre se verifica)
  • Extend: "Mostrar publicidad" <<extend>> "Ver video" (solo si el usuario no es premium)

Plantilla textual para describir un caso de uso

Un caso de uso debe documentarse de forma textual con todos los detalles necesarios para su implementación.

📝 Plantilla estándar de caso de uso:

Nombre: Registrar paciente en el sistema

Identificador: UC-001
Versión: 1.0
Autor: Equipo de desarrollo
Fecha: [fecha actual]

Actor principal: Secretaria
Actores secundarios: (ninguno)

Propósito: Almacenar la información de un nuevo paciente en la base de datos del consultorio.

Precondición: La secretaria ha iniciado sesión correctamente en el sistema.

Flujo normal de eventos (camino feliz):
1. La secretaria selecciona la opción "Nuevo paciente" desde el menú principal.
2. El sistema muestra un formulario con los campos requeridos (nombre, teléfono, correo, dirección).
3. La secretaria completa todos los campos obligatorios.
4. La secretaria hace clic en el botón "Guardar".
5. El sistema valida que todos los campos requeridos estén completos.
6. El sistema verifica que el correo electrónico no exista previamente.
7. El sistema guarda los datos del paciente en la base de datos.
8. El sistema muestra un mensaje de éxito y asigna un ID único al paciente.
9. El caso de uso termina.

Flujos alternativos (excepciones):
3a. La secretaria deja campos obligatorios vacíos:
  → El sistema muestra un error indicando los campos faltantes y vuelve al paso 3.
5a. El correo electrónico ya existe en el sistema:
  → El sistema muestra un mensaje de error y solicita otro correo, vuelve al paso 3.
6a. Error de conexión a la base de datos:
  → El sistema muestra un mensaje de error técnico y vuelve al paso 2.

Postcondición (estado final):
El paciente queda registrado en el sistema con un ID único, listo para agendar citas o recibir tratamientos.

Requisitos no funcionales asociados:
- El formulario debe cargarse en menos de 2 segundos (rendimiento)
- Los datos deben transmitirse encriptados (seguridad)
- La interfaz debe ser responsive y accesible (usabilidad)

📌 Elementos adicionales que puede incluir la plantilla:

  • Frecuencia de uso: ¿Cuántas veces se espera que se ejecute?
  • Prioridad: Alta, Media, Baja
  • Riesgos asociados: Posibles problemas durante la ejecución
  • Puntos de extensión: Lugares donde se pueden insertar comportamientos extendidos
  • Requisitos especiales: Necesidades específicas (ej: hardware especial)

📚 Profundización en Casos de Uso

1. Niveles de casos de uso (Alistair Cockburn)

Alistair Cockburn clasifica los casos de uso en diferentes niveles según su granularidad:

  • 🌊 Nivel de mar (Sea level): Casos de uso que representan interacciones básicas del usuario con el sistema. Ej: "Registrar paciente"
  • 🐟 Nivel de pez (Fish level): Casos de uso que representan subfunciones reutilizables. Ej: "Validar correo"
  • 🦐 Nivel de camarón (Shrimp level): Casos de uso de muy bajo nivel técnico. Ej: "Conectar a base de datos"
  • ☁️ Nivel de nube (Cloud level): Casos de uso de alto nivel estratégico. Ej: "Gestionar consultorio dental"
  • ⭐ Nivel de estrella (Star level): Casos de uso que representan objetivos primarios del usuario

3. Buenas prácticas para escribir casos de uso

  • ✅ Usar nombres en verbo + sustantivo (ej: "Registrar paciente", no "Paciente")
  • ✅ Mantener el flujo principal simple y directo (camino feliz)
  • ✅ Documentar todas las excepciones posibles
  • ✅ Usar lenguaje claro y sin ambigüedades
  • ✅ Incluir criterios de aceptación verificables
  • ✅ Mantener los casos de uso independientes cuando sea posible
  • ✅ Validar con stakeholders antes de implementar
  • ✅ Usar diagramas complementarios (actividades, secuencia)

4. Errores comunes al documentar casos de uso

  • ❌ Demasiada información técnica: Los casos de uso deben enfocarse en el "qué", no en el "cómo"
  • ❌ Mezclar casos de uso: Un caso de uso debe ser una funcionalidad cohesiva
  • ❌ Olvidar flujos alternativos: Las excepciones son tan importantes como el flujo principal
  • ❌ Usuarios demasiado genéricos: "Usuario" no es un actor; identificar roles específicos
  • ❌ Casos de uso demasiado grandes: Dividir funcionalidades complejas en casos más pequeños
