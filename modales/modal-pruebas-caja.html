Pruebas de Caja: Negra, Blanca y Gris

🎬 Video: Pruebas de Caja Negra, Blanca y Gris

Pruebas de Caja Negra (Black Box Testing)

Las pruebas de caja negra evalúan el software sin conocer su estructura interna. El tester solo conoce las entradas y las salidas esperadas, simulando el comportamiento de un usuario final.

📊 Esquema de prueba de caja negra:

┌─────────┐ ┌─────────────┐ ┌─────────┐
│ Entrada │ ──▶ │ SISTEMA │ ──▶ │ Salida │
│ (Input)│ │ (Caja Negra)│ │(Output) │
└─────────┘ └─────────────┘ └─────────┘
     El tester NO ve lo que pasa aquí dentro

🎯 Técnicas de prueba de caja negra:

📊 Particiones de equivalencia

Divide los datos de entrada en grupos (particiones) donde se espera el mismo comportamiento. Se prueba un valor representativo de cada partición.

Ejemplo: Edad entre 1-120 años. Particiones: (≤0), (1-120), (≥121). Se prueba con valores como 0, 60, 121.

📏 Análisis de valores límite

Prueba los valores justo en los bordes de las particiones, donde suelen ocurrir más errores.

Ejemplo: Para el rango 1-120, se prueba con 0, 1, 2, 119, 120, 121.

📋 Tablas de decisión

Muestra combinaciones de condiciones y sus acciones resultantes. Útil para lógica compleja con múltiples condiciones.

Ejemplo: Si usuario es admin Y tiene permiso → mostrar botón eliminar.

🔀 Pruebas de transición de estados

Evalúa cómo el sistema responde a diferentes secuencias de eventos o cambios de estado.

Ejemplo: Estados de un pedido: "pendiente" → "pagado" → "enviado" → "entregado".

🔗 Pruebas de casos de uso

Valida que el sistema se comporte como se especifica en los casos de uso desde la perspectiva del usuario.

📝 Pruebas de adivinación de errores

Basada en la experiencia del tester para intuir dónde pueden estar los errores más probables.

📌 Ejemplo concreto:

Probar un formulario de login. Entradas: usuario y contraseña. Salidas: acceso concedido o denegado.

  • Caso 1: Usuario correcto + Contraseña correcta → Acceso concedido
  • Caso 2: Usuario correcto + Contraseña incorrecta → Acceso denegado
  • Caso 3: Usuario inexistente + Contraseña cualquiera → Acceso denegado
  • Caso 4: Usuario vacío + Contraseña cualquiera → Mensaje de error
  • Caso 5: Usuario correcto + Contraseña vacía → Mensaje de error
✅ Ventajas de caja negra:
• No requiere conocimiento del código
• El tester no necesita ser desarrollador
• Simula al usuario real
• Imparcial (no hay sesgo del programador)

❌ Desventajas de caja negra:
• No detecta problemas internos (bucles infinitos, variables no inicializadas)
• Puede dejar caminos sin probar
• Difícil de automatizar completamente
• No ayuda a depurar errores

Pruebas de Caja Blanca (White Box Testing)

Las pruebas de caja blanca evalúan el software conociendo su estructura interna. El tester diseña pruebas específicas para recorrer todas las rutas, condiciones y ciclos del código.

📊 Esquema de prueba de caja blanca:

┌─────────────────────────────────────┐
│ CÓDIGO FUENTE │
│ if (x > 0) { │
│ resultado = x * 2; │
│ } else { │
│ resultado = 0; │
│ } │
│ return resultado; │
└─────────────────────────────────────┘
    El tester SÍ ve y analiza el código interno

🎯 Técnicas de prueba de caja blanca:

📏 Cobertura de líneas (Statement Coverage)

Ejecutar cada línea de código al menos una vez. Es el nivel mínimo de cobertura.

Objetivo: 100% de líneas ejecutadas.

🔀 Cobertura de ramas (Branch Coverage)

Ejecutar verdadero y falso de cada condición (if/else, switch, bucles).

Objetivo: 100% de ramas evaluadas.

🛣️ Cobertura de caminos (Path Coverage)

Recorrer todas las combinaciones posibles de ramas. Muy costoso para código complejo.

Objetivo: Máximo posible (práctico).

📋 Cobertura de condiciones (Condition Coverage)

Evaluar cada condición booleana individual como verdadera y falsa.

🔗 Cobertura de condiciones múltiples

Probar todas las combinaciones de condiciones en una expresión booleana.

🔄 Pruebas de bucles (Loop Testing)

Probar bucles: 0 iteraciones, 1 iteración, iteraciones típicas, máximo de iteraciones.

📌 Ejemplo concreto:

Una función que calcula descuento:

function calcularDescuento(monto, clienteFrecuente) {
    let descuento = 0;
    if (monto > 1000 && clienteFrecuente) {
        descuento = 0.10;  // 10% de descuento
    } else if (monto > 500) {
        descuento = 0.05;  // 5% de descuento
    } else {
        descuento = 0;     // sin descuento
    }
    return monto * (1 - descuento);
}

Pruebas necesarias para cobertura de ramas:

  • ✅ Caso 1: monto = 1500, clienteFrecuente = true → entra primera rama
  • ✅ Caso 2: monto = 1500, clienteFrecuente = false → no entra primera rama, entra segunda
  • ✅ Caso 3: monto = 300, clienteFrecuente = false → entra tercera rama (else)
  • ✅ Caso 4: monto = 300, clienteFrecuente = true → entra tercera rama (else)
✅ Ventajas de caja blanca:
• Detecta errores ocultos (variables no inicializadas, bucles infinitos)
• Permite optimizar código
• Identifica caminos no probados
• Útil para pruebas unitarias

❌ Desventajas de caja blanca:
• Requiere acceso al código fuente
• Necesita tester con conocimientos de programación
• Costoso y lento
• No verifica requisitos del usuario

Pruebas de Caja Gris (Gray Box Testing)

Las pruebas de caja gris son un punto medio entre caja negra y caja blanca. El tester tiene conocimiento parcial del sistema: arquitectura, tablas de base de datos, interfaces entre módulos, pero no todo el código fuente.

📊 Esquema de prueba de caja gris:

┌─────────────────────────────────────────────────────────┐
│ 🧑 Tester conoce: │
│ • Arquitectura del sistema │
│ • Estructura de base de datos │
│ • Interfaces entre módulos │
│ • API y endpoints │
│ ❌ NO conoce: │
│ • Código fuente completo │
│ • Detalles de implementación internos │
└─────────────────────────────────────────────────────────┘

🎯 ¿Cuándo se usa caja gris?

  • 🔗 Pruebas de integración entre componentes
  • 🔒 Pruebas de seguridad (simula atacante con información privilegiada)
  • 🌐 Sistemas con múltiples capas (web, base de datos, APIs)
  • 📊 Pruebas de bases de datos (consultas SQL, procedimientos almacenados)
  • 🔌 Pruebas de API (conociendo los endpoints pero no la implementación)
  • 🔄 Pruebas de regresión en sistemas complejos

📌 Ejemplo concreto:

Probar un sitio web de compras conociendo la estructura de la base de datos (tablas de productos, carrito, usuarios) pero sin acceso al código fuente del backend.

  • 📦 Se sabe que la tabla "productos" tiene una columna "precio"
  • 🛒 Se sabe que el carrito almacena items en la tabla "carrito_items"
  • 🔍 Se pueden diseñar pruebas de inyección SQL más efectivas
  • ✅ Se verifica que los datos se guarden correctamente
  • 📊 Se validan consultas complejas y procedimientos almacenados
✅ Ventajas de caja gris:
• Combina lo mejor de ambos mundos
• Más eficiente que caja negra pura
• Menos invasivo que caja blanca
• Ideal para pruebas de integración
• Excelente para pruebas de seguridad (pentesting)

❌ Desventajas de caja gris:
• No es adecuada para todas las pruebas
• Requiere cierto conocimiento técnico
• Puede ser difícil de automatizar completamente
• Depende de la calidad de la documentación

2. Cálculo de complejidad ciclomática (Caja Blanca)

La complejidad ciclomática mide el número de caminos linealmente independientes en un programa. Se calcula como:

📐 Fórmula de McCabe:
V(G) = E - N + 2
donde:
• E = número de aristas (ramas) en el grafo de flujo
• N = número de nodos (sentencias/bloques)

Interpretación:
• V(G) = 1-10 → Programa simple, bajo riesgo
• V(G) = 11-20 → Moderado, riesgo moderado
• V(G) = 21-50 → Complejo, alto riesgo
• V(G) > 50 → Inmantenible, muy alto riesgo
