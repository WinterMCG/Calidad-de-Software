📜 Estándares ISO para calidad de software

ISO/IEC 25010:2023

Sistema de calidad de producto

Define 8 características de calidad con sus subcaracterísticas. Es el estándar principal para evaluar productos de software.

Características: Adecuación funcional, Confiabilidad, Usabilidad, Eficiencia, Seguridad, Compatibilidad, Mantenibilidad, Portabilidad.

ISO/IEC 25000 (SQuaRE)

Software Quality Requirements and Evaluation

Familia de estándares que incluyen guías para especificar requisitos de calidad y evaluar productos de software.

Partes: 25010 (modelo), 25020 (medición), 25030 (calidad en uso), 25040 (evaluación).

ISO/IEC 29119

Estándar de pruebas de software

Define conceptos, procesos, documentación y técnicas para pruebas de software. Reemplaza a otros estándares de pruebas.

Partes: 29119-1 (conceptos), 29119-2 (procesos), 29119-3 (documentación), 29119-4 (técnicas).

ISO 9001:2015

Sistemas de gestión de calidad

Estándar genérico para sistemas de gestión de calidad aplicable a cualquier organización, incluyendo desarrollo de software.

Principios: Enfoque al cliente, liderazgo, participación del personal, mejora continua, toma de decisiones basada en evidencia.

ISO/IEC 27001

Seguridad de la información

Estándar para sistemas de gestión de seguridad de la información (SGSI). Relevante para pruebas de seguridad.

Controles: 114 controles en 14 dominios, incluyendo control de acceso, criptografía, seguridad física.

ISO/IEC 15504 (SPICE)

Software Process Improvement and Capability dEtermination

Estándar para evaluación y mejora de procesos de software. Alternativa a CMMI.

Niveles de capacidad: 0 Incompleto, 1 Realizado, 2 Gestionado, 3 Establecido, 4 Predecible, 5 Optimizador.

📋 Estándares IEEE para ingeniería de software

IEEE 829-2008

Documentación de pruebas

Define la estructura y contenido de los documentos de pruebas:

  • Plan de pruebas (Test Plan)
  • Diseño de casos de prueba (Test Design)
  • Casos de prueba (Test Cases)
  • Procedimientos de prueba (Test Procedures)
  • Reporte de incidentes (Test Incident Report)
  • Reporte de resumen (Test Summary Report)

IEEE 830-1998

Especificación de requisitos (SRS)

Define la estructura del documento de especificación de requisitos de software:

  • Introducción (propósito, alcance, definiciones)
  • Descripción general (perspectiva, funciones, usuarios)
  • Requisitos específicos (interfaces, funciones, rendimiento)
  • Apéndices e índice

IEEE 730-2014

Plan de aseguramiento de calidad (SQAP)

Define el contenido del plan de garantía de calidad:

  • Propósito y alcance
  • Documentos de referencia
  • Gestión (organización, tareas, responsabilidades)
  • Documentación
  • Estándares, prácticas y convenciones
  • Revisiones y auditorías
  • Pruebas
  • Gestión de problemas

IEEE 1028-2008

Revisiones técnicas formales

Define el proceso para realizar inspecciones, revisiones técnicas, auditorías y walkthroughs.

Roles: Moderador, autor, revisor, registrador, presentador.

IEEE 1044-2009

Clasificación de anomalías

Define un esquema estándar para clasificar y reportar anomalías (defectos, problemas, incidentes).

Atributos: Severidad, prioridad, estado, origen, tipo.

IEEE 610.12-1990

Glosario de términos

Define terminología estándar para ingeniería de software, incluyendo términos de calidad y pruebas.

🤖 Automatización de pruebas

📌 ¿Qué es la automatización de pruebas?
Es el uso de software para controlar la ejecución de pruebas, comparar resultados esperados vs reales, y reportar resultados sin intervención manual.

✅ Beneficios de la automatización:
• Mayor velocidad de ejecución
• Reducción de errores humanos
• Ejecución frecuente (cada commit, nightly)
• Cobertura de pruebas consistente
• Libera tiempo de testers para pruebas exploratorias
• Rápida retroalimentación a desarrolladores

❌ Cuándo NO automatizar:
• Pruebas que se ejecutan solo una vez
• Pruebas que cambian constantemente
• Pruebas con alta inversión inicial y bajo retorno
• Pruebas exploratorias/usabilidad

📌 Ejemplo de pipeline de automatización (CI/CD):
1. Developer hace push al repositorio
2. GitHub Actions / GitLab CI / Jenkins detecta el cambio
3. Se ejecutan pruebas unitarias (rápidas, < 5 min)
4. Si pasan, se construye la aplicación
5. Se despliega en entorno de pruebas
6. Se ejecutan pruebas de integración (< 15 min)
7. Se ejecutan pruebas E2E/UI (más lentas, < 30 min)
8. Si todas pasan, se puede desplegar a producción

📊 Cuándo usar cada una:

✅ Selenium: Proyectos grandes con múltiples lenguajes, testing cross-browser, aplicaciones legadas.
✅ Cypress: Proyectos modernos con JavaScript/TypeScript, equipos pequeños, aplicaciones SPA (React/Angular/Vue).
✅ Playwright: Proyectos que requieren la máxima velocidad y confiabilidad, testing cross-browser moderno.
✅ Puppeteer: Proyectos que solo necesitan Chrome/Chromium, web scraping, pruebas de rendimiento.
