📌 Clasificación general: funcionales vs no funcionales
Pruebas funcionales: unitarias, componentes, integración, sistema, humo, aceptación, regresión, interfaz.
Pruebas no funcionales: rendimiento, carga/estrés, seguridad, escalabilidad, confiabilidad, instalación, conformidad, compatibilidad.

📌 Resumen completo: Las pruebas de software se clasifican en múltiples tipos según su objetivo (unitarias, integración, sistema, regresión, etc.) y su enfoque (caja negra, caja blanca, carga, seguridad, usabilidad). Aplicar la combinación adecuada garantiza la fiabilidad, el rendimiento y la satisfacción del usuario final. Una estrategia de pruebas equilibrada sigue la Pirámide de Mike Cohn: muchas pruebas unitarias rápidas y baratas en la base, menos pruebas de integración en el medio, y pocas pruebas end-to-end lentas y costosas en la cima.

📌 Dato clave: El costo de corregir un error aumenta exponencialmente cuanto más tarde se detecta. Detectar un bug en pruebas unitarias cuesta 1x, en integración 5x, en sistema 15x, en producción 30x o más.

🏔️ La Pirámide de pruebas (Mike Cohn)

La pirámide de pruebas es un concepto fundamental en ingeniería de software que recomienda la distribución óptima de los diferentes tipos de pruebas. Fue popularizada por Mike Cohn en su libro "Succeeding with Agile".

📌 La pirámide original de Mike Cohn: base ancha (unitarias), centro (integración), cúspide (E2E/UI).
📌 ¿Qué nos enseña esta pirámide?

La pirámide de Mike Cohn es una guía para diseñar una estrategia de pruebas eficiente. Su forma indica dónde debemos poner el mayor esfuerzo de automatización:
  • 🔹 Base (Pruebas Unitarias): Deben ser la capa más grande. Son pruebas rápidas, aisladas y económicas que verifican funciones o métodos individuales. Una buena práctica es que constituyan alrededor del 70% del total de pruebas.
  • 🔹 Capa Media (Pruebas de Integración / API): Un número moderado. Verifican que los componentes interactúen correctamente entre sí y con servicios externos (bases de datos, APIs). Lo ideal es que representen cerca del 20%.
  • 🔹 Cúspide (Pruebas End-to-End / UI): Es la capa más pequeña. Simulan flujos completos de usuario a través de la interfaz gráfica. Son las más lentas, costosas y frágiles de mantener, por lo que se recomienda que sean solo un 5-10% del total.
🎯 Objetivo final: Invertir el esfuerzo donde más rendimiento obtenemos: muchas pruebas rápidas y baratas en la base, y pocas pruebas lentas y costosas en la cima. Esto acelera la retroalimentación al equipo y reduce drásticamente los costos de corrección.
⚠️ Antipatrón: La pirámide invertida (ice cream cone / cono de helado)

Cuando el equipo invierte excesivamente en pruebas End-to-End (UI) y descuida las pruebas unitarias, la distribución se invierte: muchas pruebas lentas y frágiles arriba y pocas pruebas rápidas abajo. Esto genera:
  • ❌ Ejecuciones de prueba muy lentas (minutos u horas).
  • ❌ Alta fragilidad: pequeños cambios en la interfaz rompen muchas pruebas.
  • ❌ Retroalimentación tardía para los desarrolladores.
  • ❌ Costos de mantenimiento elevados (cambiar una prueba UI puede tomar horas).
  • ❌ Falsos positivos frecuentes que generan desconfianza en el equipo.
✅ Solución: Seguir la pirámide clásica: priorizar pruebas unitarias, luego integración, y solo unas pocas pruebas UI para validar flujos críticos.

📊 Distribución recomendada:

  • 70-80% Pruebas unitarias
  • 15-20% Pruebas de integración
  • 5-10% Pruebas E2E / Aceptación

💰 Costo relativo de corrección:

  • Unitarias: 1x
  • Integración: 5x
  • Sistema: 15x
  • Producción: 30x-100x

⚡ Velocidad de ejecución:

  • Unitarias: milisegundos
  • Integración: segundos
  • E2E / Aceptación: minutos
📌 Principios de la pirámide:
✅ Más pruebas abajo: Invertir en pruebas unitarias rápidas y baratas
✅ Menos pruebas arriba: Limitar pruebas end-to-end lentas y costosas
✅ Test early, test often: Probar temprano y frecuentemente
✅ Automatizar siempre que sea posible: Especialmente unitarias e integración
✅ Mantener la pirámide: Evitar la "pirámide invertida"
✅ Pruebas confiables: Las pruebas no deben ser flaky (resultados inconsistentes)
📊 Evolución de la pirámide - Pirámide de pruebas moderna:

/\\
/ \\ ← Pruebas E2E / UI (menos, críticas)
/ \\
/ \\ ← Pruebas de Integración / API
/________\\
← Pruebas Unitarias (muchas, rápidas)

En la práctica moderna, también se incluyen pruebas de contrato (Pact), pruebas de componentes, y pruebas de seguridad en la capa media.

🧪 Pruebas Unitarias (Unit Testing)

Las pruebas unitarias verifican el correcto funcionamiento de componentes individuales del software (funciones, métodos, clases) de forma aislada. Son la base de la pirámide de pruebas y deben ser las más numerosas.

📌 Características de las pruebas unitarias:

✅ Alcance: Una función o método a la vez
✅ Responsable: Desarrollador
✅ Velocidad: Milisegundos (miles por segundo)
✅ Aislamiento: Sin dependencias externas (BD, API, red, sistema de archivos)
✅ Automatización: Fácil de automatizar (se ejecutan en CI/CD)
✅ Frecuencia: Cada vez que se compila/cambia el código
✅ Mantener bajo acoplamiento para facilitar pruebas

📝 Ejemplo de prueba unitaria (Python con pytest):

# Código a probar
def calcular_descuento(precio, porcentaje):
    """Calcula el descuento aplicado a un precio."""
    if precio <= 0 or porcentaje < 0:
        return 0
    if porcentaje > 100:
        porcentaje = 100  # No más del 100% de descuento
    return precio * (porcentaje / 100)

def aplicar_iva(precio, iva=21):
    """Aplica IVA a un precio."""
    if precio < 0:
        raise ValueError("El precio no puede ser negativo")
    return precio * (1 + iva / 100)

# Pruebas unitarias con pytest
import pytest

def test_calcular_descuento():
    assert calcular_descuento(100, 10) == 10
    assert calcular_descuento(200, 25) == 50
    assert calcular_descuento(0, 10) == 0
    assert calcular_descuento(100, -5) == 0
    assert calcular_descuento(100, 150) == 100  # 100% descuento
    assert calcular_descuento(50.5, 10) == 5.05  # floats

def test_aplicar_iva():
    assert aplicar_iva(100) == 121
    assert aplicar_iva(100, 10) == 110
    assert aplicar_iva(0) == 0
    with pytest.raises(ValueError):
        aplicar_iva(-50)
📌 Buenas prácticas en pruebas unitarias:
• Nomenclatura clara: test_[nombre_funcion]_[escenario]_[resultado_esperado]
• Una aserción por prueba (preferiblemente): Cada prueba verifica una cosa
• Independencia: Las pruebas no deben depender unas de otras
• Rápida ejecución: Deben correr en milisegundos
• Mocks y stubs: Aislar dependencias externas
• Fixture: Datos de prueba reutilizables
• Cobertura: Apuntar a 80%+ de cobertura de código

✅ Beneficios de las pruebas unitarias:
• 🔍 Detectan errores temprano en el desarrollo (segundos después de escribir el código)
• 🔄 Facilitan la refactorización (cambiar código con confianza, sabiendo que las pruebas pasan)
• 📚 Sirven como documentación viva del código (ejemplos de uso)
• ⏱️ Reducen el tiempo de debugging (hasta un 50%)
• 🎯 Mejoran el diseño del código (forzan a escribir código testeable, con bajo acoplamiento)
• 🤖 Automatizables en CI/CD (se ejecutan en cada commit)
• 💰 Ahorran dinero (detectar errores temprano cuesta 30-100 veces menos que en producción)

❌ Limitaciones:
• 🔗 No detectan errores de integración entre módulos
• 🌐 No verifican el sistema completo
• 🔧 Pueden ser frágiles si el código cambia mucho (mucho refactoring sin rediseño)
• 🚫 No reemplazan las pruebas de sistema o aceptación
📊 Métricas de pruebas unitarias:
• Cobertura de código: Porcentaje de líneas/ramas ejecutadas por las pruebas. Objetivo típico: 80%.
• Tiempo de ejecución: Debe ser menor a 1 minuto para miles de pruebas.
• Tasa de falsos positivos: Idealmente 0% (pruebas flaky son malas).
• Tiempo medio entre fallos (MTBF) de pruebas: Qué tan estable es el conjunto.

🧩 Pruebas de Componentes (Component Testing)

Las pruebas de componentes verifican el comportamiento de componentes individuales del software (módulos, clases, microservicios) en un entorno controlado, pero a un nivel más amplio que las pruebas unitarias.

📌 ¿Qué son las pruebas de componentes?
Las pruebas de componentes (también llamadas pruebas de módulos) son procesos de prueba de componentes individuales aislados. Es un proceso de prueba de defectos que se enfoca en verificar que cada componente funcione según sus especificaciones.
📌 ¿Qué se puede probar como componente?
• 🔹 Funciones individuales o métodos dentro de un objeto
• 🔹 Clases de objetos con varios atributos y métodos
• 🔹 Componentes compuestos con interfaces definidas (API, librerías)
• 🔹 Microservicios de manera aislada (con dependencias mockeadas)
• 🔹 Plugins o extensiones del sistema principal
✅ Diferencia entre pruebas unitarias y de componentes:
AspectoPruebas UnitariasPruebas de Componentes
AlcanceFunción/método individualClase/módulo/microservicio
AislamientoTotal (mocks)Parcial (dependencias reales o simuladas)
ResponsableDesarrolladorDesarrollador/QA
VelocidadMuy rápida (ms)Rápida (ms-segundos)
📌 Estrategias para pruebas de componentes:
• Enfoque de caja negra: Se prueba el componente según sus entradas y salidas esperadas, sin conocer su implementación interna.
• Enfoque de caja blanca: Se prueba la estructura interna del componente (caminos, condiciones).
• Pruebas de interfaz del componente: Verificar que el componente expone correctamente su API.
• Pruebas de manejo de errores: Cómo responde el componente a entradas inválidas o excepciones.
📝 Ejemplo de prueba de componente (Java con JUnit y Mockito): 
// Componente: Servicio de usuarios
public class UserService {
    private UserRepository repository;
    private EmailService emailService;
    
    public User registerUser(String email, String password) {
        if (repository.findByEmail(email) != null) {
            throw new UserAlreadyExistsException();
        }
        User user = new User(email, password);
        repository.save(user);
        emailService.sendWelcomeEmail(email);
        return user;
    }
}

// Prueba de componente
@ExtendWith(MockitoExtension.class)
public class UserServiceTest {
    @Mock UserRepository repository;
    @Mock EmailService emailService;
    @InjectMocks UserService service;
    
    @Test
    void shouldRegisterNewUser() {
        when(repository.findByEmail("test@test.com")).thenReturn(null);
        
        User user = service.registerUser("test@test.com", "pass");
        
        assertNotNull(user);
        verify(repository).save(any(User.class));
        verify(emailService).sendWelcomeEmail("test@test.com");
    }
    
    @Test
    void shouldThrowExceptionIfUserExists() {
        when(repository.findByEmail("existing@test.com")).thenReturn(new User());
        
        assertThrows(UserAlreadyExistsException.class, 
            () -> service.registerUser("existing@test.com", "pass"));
    }
}
🔧 Herramientas comunes para pruebas de componentes:
• JUnit / TestNG (Java): Con Mockito para mocks y AssertJ para aserciones
• pytest (Python): Con unittest.mock o pytest-mock
• Jest (JavaScript/TS): Con su sistema de mocks integrado
• xUnit (C# / .NET): Con Moq o NSubstitute
• PHPUnit (PHP): Con Mockery o Prophecy
• RSpec (Ruby): Con doubles y mocks integrados
✅ Buenas prácticas:
• 🔄 Mantener los componentes pequeños y con una única responsabilidad (principio SRP)
• 🔌 Usar inyección de dependencias para facilitar el mockeo
• 📝 Documentar las interfaces de los componentes
• 🧪 Probar tanto casos felices como casos de error
• 🔁 Ejecutar pruebas de componentes en cada build (CI/CD)

🖥️ Pruebas de Interfaz de Usuario (UI Testing)

Las pruebas de interfaz de usuario verifican que los elementos visuales e interactivos de una aplicación (botones, formularios, menús, ventanas) funcionen correctamente y ofrezcan una experiencia de usuario coherente y sin errores.

📌 Aspectos clave a probar en UI:

🎨 Diseño y maquetación: Alineación, espaciado, colores, tipografías, tamaños de fuente, bordes, sombras.
🖱️ Interactividad: Botones, enlaces, menús desplegables, efectos hover/active/disabled, desplazamiento (scroll).
📱 Diseño adaptable (Responsive): Funcionamiento en diferentes resoluciones (1920x1080, 1366x768, 375x667), orientación vertical/horizontal.
♿ Accesibilidad: Navegación por teclado (tab, enter, espacio), contraste de colores (WCAG 2.1 AA), lectores de pantalla (NVDA, VoiceOver), atributos ARIA.
🌐 Compatibilidad: Diferentes navegadores (Chrome, Firefox, Safari, Edge) y sistemas operativos.
🔄 Comportamiento dinámico: Carga de datos asíncrona, spinners, skeletons loaders, animaciones.
❌ Manejo de errores UI: Mensajes de error visibles y comprensibles, validación de formularios en tiempo real.
📌 Tipos de pruebas de UI:
• Pruebas visuales (Visual regression): Comparan capturas de pantalla para detectar cambios no deseados.
• Pruebas funcionales de UI: Simulan interacciones del usuario (clics, escritura, envío de formularios).
• Pruebas de flujo (End-to-end): Validan recorridos completos de usuario (ej: registro → login → compra).
• Pruebas de accesibilidad: Verifican que la UI sea usable por personas con discapacidades.
• Pruebas de internacionalización (i18n): Verifican que la UI se muestre correctamente en diferentes idiomas.
📝 Ejemplo de prueba de UI con Selenium (Python): 
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.common.keys import Keys

def test_login_ui():
    driver = webdriver.Chrome()
    driver.get("https://ejemplo.com/login")
    
    # Verificar que los elementos existen y son visibles
    email_input = driver.find_element(By.ID, "email")
    password_input = driver.find_element(By.ID, "password")
    login_button = driver.find_element(By.ID, "login-btn")
    
    assert email_input.is_displayed()
    assert password_input.is_displayed()
    assert login_button.is_displayed()
    
    # Simular interacción
    email_input.send_keys("usuario@ejemplo.com")
    password_input.send_keys("contraseña123")
    login_button.click()
    
    # Verificar redirección
    assert "dashboard" in driver.current_url
    
    driver.quit()

✅ Buenas prácticas en pruebas de UI:
• 🎯 No automatizar todas las pruebas UI (son lentas y frágiles). Priorizar flujos críticos.
• 🔧 Usar selectores robustos: data-testid, id, name. Evitar XPath frágiles o selectores CSS muy anidados.
• ⏱️ Ejecutar pruebas UI en CI/CD solo para cambios relevantes (no después de cada commit).
• 🖼️ Considerar pruebas visuales con herramientas como Percy, BackstopJS o Chromatic.
• 🔁 Mantener las pruebas independientes (no dependen unas de otras).
• 🧹 Limpiar datos de prueba después de ejecutar (evitar efectos colaterales).

🔗 Pruebas de Integración (Integration Testing)

Las pruebas de integración verifican que los diferentes módulos o componentes del sistema funcionen correctamente cuando se combinan. Detectan errores en las interfaces y en la comunicación entre componentes.

📌 Tipos de integración:

🔹 Integración ascendente (Bottom-Up):
  ✓ Se prueban primero los módulos de bajo nivel (ej: acceso a datos)
  ✓ Luego se integran con módulos de alto nivel (lógica de negocio)
  ✓ Se usan "drivers" para simular módulos de alto nivel
  ✓ Ventaja: Fácil de aislar errores en capas inferiores

🔹 Integración descendente (Top-Down):
  ✓ Se prueban primero los módulos de alto nivel (ej: UI)
  ✓ Se usan "stubs" para simular módulos de bajo nivel
  ✓ Ventaja: Se prueba la lógica principal temprano

🔹 Integración big bang:
  ✓ Se integran todos los módulos a la vez
  ✓ Alto riesgo, difícil de depurar (no se sabe qué módulo falla)
  ✓ ❌ No recomendada para sistemas grandes

🔹 Integración incremental (la recomendada):
  ✓ Se integran módulos de uno en uno o en pequeños grupos
  ✓ Más fácil de localizar errores
  ✓ ✅ Recomendada para la mayoría de proyectos

📝 Ejemplo de prueba de integración (API con Supertest y Node.js):

const request = require('supertest');
const app = require('../app');
const db = require('../db');

describe('API de usuarios - Pruebas de integración', () => {
    beforeAll(async () => {
        await db.connect();  // Conectar a BD de prueba
        await db.clear();    // Limpiar datos previos
    });
    
    afterAll(async () => {
        await db.disconnect();
    });
    
    test('POST /api/usuarios debe crear un usuario válido', async () => {
        const nuevoUsuario = {
            nombre: 'Juan Pérez',
            email: 'juan@ejemplo.com',
            password: '123456'
        };
        
        const response = await request(app)
            .post('/api/usuarios')
            .send(nuevoUsuario);
            
        expect(response.statusCode).toBe(201);
        expect(response.body).toHaveProperty('id');
        expect(response.body.email).toBe('juan@ejemplo.com');
        expect(response.body.password).toBeUndefined(); // No devolver password
    });
    
    test('GET /api/usuarios debe devolver lista de usuarios', async () => {
        const response = await request(app)
            .get('/api/usuarios');
            
        expect(response.statusCode).toBe(200);
        expect(Array.isArray(response.body)).toBe(true);
        expect(response.body.length).toBeGreaterThan(0);
    });
});
✅ Beneficios de las pruebas de integración:
• 🔗 Detectan errores en las interfaces entre módulos (parámetros incorrectos, formatos de datos)
• 🔄 Verifican el flujo de datos entre componentes
• 🌐 Prueban la comunicación con sistemas externos (bases de datos reales, APIs reales)
• 📈 Aumentan la confianza en el sistema completo
• 🐛 Ayudan a encontrar bugs que las pruebas unitarias no detectan (efectos colaterales)
📌 Estrategias de integración con servicios externos:
• Bases de datos reales: Usar una BD de prueba separada, resetear entre pruebas.
• APIs externas: Usar WireMock o similares para simular respuestas.
• Mensajería (colas): Usar brokers embebidos (RabbitMQ embebido, Kafka con TestContainers).
• Contenedores (Docker): Usar TestContainers (Java) o docker-compose para levantar dependencias reales.
🔧 Herramientas para pruebas de integración:
• Supertest (Node.js): Para probar APIs HTTP
• Spring Boot Test (Java): @SpringBootTest para pruebas de integración
• pytest (Python): Con pytest-django o pytest-flask
• TestContainers (Java, Go, .NET): Levanta contenedores Docker para pruebas
• WireMock: Simula APIs externas
• H2 / SQLite: Bases de datos en memoria para pruebas

🌐 Pruebas de Sistema (System Testing)

Las pruebas de sistema evalúan el software completo e integrado en un entorno similar al de producción. Verifican que el sistema cumpla con todos los requisitos especificados (funcionales y no funcionales). Es la última fase de pruebas antes de la aceptación del cliente.

📌 Tipos de pruebas de sistema:

🧪 Pruebas funcionales: Verifican que todas las funcionalidades cumplan los requisitos
⚡ Pruebas de rendimiento: Evalúan tiempos de respuesta, consumo de recursos
🔒 Pruebas de seguridad: Verifican la protección contra amenazas
🎨 Pruebas de usabilidad: Evalúan la facilidad de uso
🔄 Pruebas de compatibilidad: Verifican funcionamiento en diferentes entornos
🔧 Pruebas de recuperación: Evalúan la capacidad de recuperarse de fallos
🌍 Pruebas de localización (L10n): Verifican adaptación a diferentes idiomas/regiones
📱 Pruebas multiplataforma: Verifican funcionamiento en diferentes dispositivos
🔐 Pruebas de autenticación y autorización: Roles, permisos, SSO
📌 Entorno de pruebas de sistema:
• Debe ser lo más parecido posible a producción (hardware, software, red, datos).
• Usar datos realistas (anonymizados si contienen información sensible).
• Configurar monitoreo para medir rendimiento y logs.
• Idealmente, un entorno separado (staging) donde no afecte a usuarios reales.
✅ Beneficios de las pruebas de sistema:
• 🎯 Verifican que el sistema cumpla con todos los requisitos especificados (validación).
• 🔍 Detectan problemas de integración final que pruebas unitarias/integración no vieron.
• 👥 Simulan el uso real del sistema por parte de los usuarios.
• 🛡️ Son la última línea de defensa antes del despliegue a producción.
• 📊 Proveen métricas de calidad del sistema antes del lanzamiento.
❌ Limitaciones de las pruebas de sistema:
• 💰 Costosas y lentas de ejecutar (pueden tomar horas o días).
• 🖥️ Requieren un entorno de prueba completo (hardware, redes, bases de datos).
• 🤖 Difíciles de automatizar completamente (requieren intervención manual en muchos casos).
• ⏰ Los errores son más costosos de corregir en esta fase (se requiere reintregar).
• 🔧 Pueden requerir configuración manual compleja.

✅ Pruebas de Aceptación (Acceptance Testing)

Las pruebas de aceptación son realizadas por el cliente o usuario final para determinar si el software está listo para ser entregado y cumple con sus necesidades. Son la última fase antes del despliegue a producción.

🧪 Pruebas alfa (Alpha Testing)

Realizadas internamente por el equipo de prueba en el entorno de desarrollo, antes de liberar al cliente.

Características: Entorno controlado, equipo interno (testers + desarrolladores), detecta bugs obvios y problemas funcionales graves.

🌍 Pruebas beta (Beta Testing)

Realizadas por un grupo selecto de usuarios reales en sus propios entornos, antes del lanzamiento oficial.

Características: Entorno real, feedback de usuarios reales, detecta problemas de usabilidad y casos de uso no previstos.

📌 Tipos adicionales de pruebas de aceptación:
• UAT (User Acceptance Testing): Realizada por usuarios finales o sus representantes.
• OAT (Operational Acceptance Testing): Verifica aspectos operativos (backup, recuperación, mantenimiento, seguridad).
• BAT (Business Acceptance Testing): Verifica que el software cumple con los objetivos de negocio.
• Contract Acceptance Testing: Verifica que el software cumple con lo especificado en el contrato.
• Regulatory Acceptance Testing: Verifica cumplimiento con normativas legales.

✅ Criterios de aceptación (características SMART):
• Specific (Específico): Sin ambigüedades. Ej: "El botón debe estar en azul" no "El botón debe verse bien".
• Measurable (Medible): Se puede verificar. Ej: "El tiempo de respuesta debe ser menor a 2 segundos".
• Achievable (Alcanzable): Realista técnicamente.
• Relevant (Relevante): Aporta valor al negocio.
• Time-bound (Con plazo): Tiene fecha límite (si aplica para entregas parciales).
📊 Métricas de pruebas de aceptación:
• Tasa de aprobación: Porcentaje de criterios de aceptación que pasan.
• Número de defectos encontrados por el usuario: Idealmente muy bajo (0-5).
• Tiempo de ejecución de UAT: Debe ser planificado (1-2 semanas típicamente).
• Satisfacción del usuario: Encuestas post-UAT.
✅ Buenas prácticas para UAT:
• 👥 Involucrar a los usuarios reales desde el principio (mostrarles prototipos, mockups).
• 📋 Definir criterios de aceptación claros y acordados ANTES de empezar el desarrollo.
• 🔧 Proporcionar un entorno de prueba estable y documentación de soporte.
• 📊 Recopilar feedback estructurado (encuestas, formularios de defectos).
• 🔄 Planificar ciclos de corrección basados en feedback de UAT.
• 📝 Documentar la decisión final de aceptación o rechazo.

🔄 Pruebas de Regresión (Regression Testing)

Las pruebas de regresión verifican que los cambios recientes (nuevas funcionalidades, correcciones de bugs, refactorizaciones) no hayan roto las funcionalidades existentes. Son críticas en entornos ágiles y CI/CD.

📌 Cuándo ejecutar pruebas de regresión:

🔄 Después de cada cambio en el código (idealmente en CI/CD, cada commit)
🔄 Antes de cada lanzamiento o despliegue (sprint release, daily build)
🔄 Cuando se corrigen bugs (verificar que la corrección no rompa algo más)
🔄 Al agregar nuevas funcionalidades (el nuevo código puede afectar al existente)
🔄 Al refactorizar código (cambios estructurales sin cambiar funcionalidad)
🔄 Al actualizar dependencias o librerías (nuevas versiones pueden tener breaking changes)
🔄 Al migrar de versión de lenguaje/framework
📊 Estrategias para pruebas de regresión:
EstrategiaDescripciónVentajasDesventajas
Regresión completaEjecutar todas las pruebasMáxima cobertura, seguroMuy lento, costoso (horas-días)
Regresión selectivaEjecutar solo pruebas relacionadasRápido, eficienteRiesgo de omitir áreas afectadas
Regresión priorizadaEjecutar pruebas por prioridadEquilibrio entre tiempo y coberturaRequiere definir prioridades
Regresión híbridaCombinación de estrategiasFlexible, adaptableMás compleja de gestionar
📌 Técnicas para reducir el conjunto de regresión:
• Análisis de impacto (Impact Analysis): Identificar qué partes del código cambiaron y qué pruebas las cubren.
• Priorización de pruebas: Ejecutar primero pruebas de funcionalidades críticas.
• Pruebas de humo: Conjunto mínimo de pruebas para validar que el build no está completamente roto.
• Minimización de pruebas: Eliminar pruebas redundantes u obsoletas.
• Selección basada en código modificado (Code-change based): Solo ejecutar pruebas que cubren el código que cambió.
✅ Mejores prácticas para pruebas de regresión:
• 🤖 Automatizar las pruebas de regresión tanto como sea posible (unitarias, integración, API).
• 📦 Mantener un conjunto de pruebas "humo" rápidas para ejecutar siempre (menos de 5 minutos).
• 🎯 Identificar y priorizar las pruebas más críticas (P0, P1, P2).
• 🔧 Usar herramientas de CI/CD (Jenkins, GitHub Actions, GitLab CI, CircleCI).
• 📊 Monitorear el tiempo de ejecución y optimizar pruebas lentas.
• 🔄 Ejecutar regresión en cada commit al menos el conjunto rápido.
• 📝 Documentar los resultados y tendencias (histórico de fallos).
• 🧹 Revisar periódicamente y eliminar pruebas obsoletas o frágiles (flaky tests).
🔧 Herramientas para automatización de regresión:
• JUnit + Maven/Gradle (Java): Ejecutar pruebas en cada build
• pytest (Python): Con plugins para ejecución selectiva
• Jest (JavaScript): --findRelatedTests para pruebas relacionadas
• TestNG (Java): Soporte para grupos y prioridades
• GitHub Actions / GitLab CI: Ejecutar pruebas automáticamente
• Jenkins Pipeline: Con etapas de regresión
📊 Métricas clave de regresión:
• Tiempo de ejecución total: Debe mantenerse bajo control (ej: < 30 minutos para regresión completa).
• Tasa de fallos: Porcentaje de ejecuciones que fallan. Muchos fallos pueden indicar código frágil.
• Pruebas flaky: Número de pruebas que fallan intermitentemente. Idealmente 0.
• Cobertura de regresión: % de funcionalidades críticas cubiertas.

🎬 Video: Pruebas de humo

📌 Qué son las pruebas de humo y cómo implementarlas.

💨 Pruebas de Humo (Smoke Testing)

Las pruebas de humo son un conjunto de pruebas rápidas y superficiales que verifican que las funcionalidades más críticas del sistema funcionan antes de realizar pruebas más profundas. Su objetivo es detectar builds completamente rotos de forma temprana.

📌 Origen del nombre:
Proviene del hardware: cuando se encendía un dispositivo electrónico (como una placa de circuito), si salía humo significaba que había un problema grave (corto circuito). Si no salía humo, se podía proceder a probar más a fondo.

🎯 ¿Qué probar en pruebas de humo?

  • 🚀 El sistema inicia correctamente (sin errores de carga)
  • 🔐 Las páginas principales cargan (login, dashboard, home)
  • 🔄 Los flujos críticos funcionan (registro, login, compra, pago)
  • 🔌 Las conexiones a servicios externos funcionan (BD, APIs, Redis)
  • 📱 Las pantallas principales en dispositivos móviles cargan (si aplica)
  • ⚡ La respuesta no es extremadamente lenta (p95 < 5 segundos)
  • ❌ No hay errores 500 o excepciones no manejadas
✅ Ventajas de las pruebas de humo:
• ⚡ Rápidas: Minutos, no horas. Típicamente 5-10 minutos.
• 🔍 Detectan problemas críticos temprano: No se pierde tiempo probando builds rotas en profundidad.
• ⏰ Ahorran tiempo: Si falla humo, se rechaza el build inmediatamente.
• 🤖 Fáciles de automatizar: Se pueden ejecutar en CI/CD en cada commit.
• 📈 Mejoran la confianza en el build: Si pasa humo, el build es mínimamente estable.
• 👥 Útiles para tests manuales: El tester puede hacer humo rápido antes de empezar pruebas detalladas.
❌ Limitaciones de las pruebas de humo:
• 🐛 No detectan errores sutiles o específicos.
• 🚫 No reemplazan las pruebas funcionales completas.
• 🎯 Solo verifican lo más básico (no profundizan).
• 🔄 Pueden dar falsa sensación de seguridad si se usan como única prueba.

✅ Página de login carga (status 200, tiempo: 0.3s)
✅ Usuario puede iniciar sesión con credenciales válidas
✅ Dashboard carga después del login (status 200)
✅ Listado de productos carga (status 200)
✅ Se puede agregar un producto al carrito
✅ Carrito muestra el producto agregado correctamente
✅ Página de checkout carga (status 200)

⚠️ RESULTADO: 8/8 pruebas PASARON
✅ Build considerado "smoke safe" - proceder a pruebas completas

AlcanceFuncionalidades críticas (todas)Solo área afectada por cambios

📌 Cómo realizar pruebas de carga y estrés con herramientas gratuitas.

⚡ Pruebas de Carga y Estrés

Evalúan el comportamiento del sistema bajo condiciones normales y extremas de uso (muchos usuarios concurrentes, grandes volúmenes de datos, picos de tráfico). Son fundamentales para aplicaciones web, APIs y microservicios.

📊 Pruebas de carga (Load Testing)

Simulan cargas esperadas de usuarios o transacciones para verificar que el sistema responde dentro de los límites aceptables.

Objetivos: Tiempo de respuesta, throughput, uso de CPU/memoria, estabilidad bajo carga normal.

Ejemplo: Simular 1000 usuarios concurrentes durante 30 minutos.

💥 Pruebas de estrés (Stress Testing)

Llevan el sistema más allá de sus límites para ver cómo falla y si se recupera adecuadamente.

Objetivos: Punto de quiebre, comportamiento durante fallos, capacidad de recuperación, detección de fugas de memoria.

Ejemplo: Aumentar carga gradualmente hasta que el sistema falle (ej: 5000 usuarios).

📌 Otros tipos de pruebas de rendimiento:
• Prueba de resistencia (Soak/Endurance): Someter el sistema a carga sostenida durante horas/días para detectar fugas de memoria o degradación progresiva.
• Prueba de pico (Spike): Incremento repentino de carga (ej: promoción de Black Friday) para ver cómo reacciona el sistema.
• Prueba de volumen: Probar con grandes cantidades de datos (millones de registros en BD).
• Prueba de concurrencia: Verificar que múltiples usuarios accediendo a la vez no corrompen datos.

✅ Métricas clave en pruebas de carga:
• ⏱️ Tiempo de respuesta: promedio, p90, p95, p99. El p99 indica experiencia del 1% más lento.
• 📊 Throughput: Peticiones por segundo (RPS) o transacciones por segundo (TPS).
• 💾 Uso de recursos: CPU, memoria, disco, red (monitorizar contenedores/servidores).
• ❌ Tasa de errores: Timeouts, HTTP 500, 503, conexiones rechazadas.
• 👥 Usuarios concurrentes máximos: Capacidad del sistema.
• 🔄 Tiempo de recuperación: Cuánto tarda el sistema en estabilizarse tras una sobrecarga.
✅ Buenas prácticas:
• 📈 Probar desde entornos aislados (no afectar producción).
• 🔁 Automatizar pruebas en CI/CD para detectar regresiones de rendimiento.
• 📊 Establecer umbrales (thresholds) para marcar fallos (ej: p95 > 500ms).
• 🧹 Limpiar datos de prueba después de ejecutar (evitar saturar BD).
• 📝 Documentar resultados y comparar con versiones anteriores.
• 🎯 Simular comportamiento realista: Tiempos de think time, navegación real.

📌 ¿Qué son las pruebas de rendimiento?
Evalúan la velocidad, capacidad de respuesta y estabilidad de un sistema bajo una carga de trabajo específica. El objetivo es identificar cuellos de botella, optimizar recursos y garantizar que la experiencia del usuario sea satisfactoria.

• 📈 Prueba de escalabilidad (Scalability): Capacidad de aumentar recursos.
• ⏱️ Prueba de resistencia (Soak/Endurance): Comportamiento durante períodos prolongados (horas/días).
• 🚀 Prueba de pico (Spike): Reacción ante aumentos repentinos de carga.
• 💾 Prueba de volumen (Volume): Manejo de grandes cantidades de datos.

• 📝 Documentar umbrales y objetivos de rendimiento (SLOs/SLIs).

📈 Pruebas de Escalabilidad (Scalability Testing)

🎬 Video: Escalabilidad en pruebas de performance (PedidosYa)

📌 Caso real de pruebas de escalabilidad en PedidosYa.
📌 ¿Qué son las pruebas de escalabilidad?
Verifican la capacidad del sistema para aumentar o disminuir recursos (servidores, memoria, instancias, nodos) y mantener o mejorar el rendimiento. Son críticas en arquitecturas cloud y microservicios.
📌 Tipos de escalabilidad:
🔹 Escalado vertical (Scale Up / Scale Down): Aumentar/disminuir recursos de una sola máquina (más CPU, más RAM, más disco). Límite: hardware máximo.
🔹 Escalado horizontal (Scale Out / Scale In): Añadir/quitar más máquinas/servidores al clúster. Teóricamente ilimitado (sujeto a costos).
🔹 Escalado de base de datos: Particionamiento (sharding), réplicas de lectura, escritura distribuida.
🔹 Escalado de caché: Añadir nodos a clúster de Redis/Memcached.
🔹 Escalado de colas: Aumentar consumidores para procesar mensajes más rápido.
📊 Métricas clave de escalabilidad:
• Speedup: ¿Cuánto mejora el rendimiento al duplicar recursos? Speedup ideal = 2x.
• Eficiencia: Speedup / Número de recursos. Ejemplo: 1.8x / 2 = 90% eficiencia.
• Punto de quiebre (Breakpoint): A partir de qué punto añadir recursos deja de ser efectivo (ley de rendimientos decrecientes).
• Escalabilidad negativa: Cuando añadir recursos empeora el rendimiento (sobrecarga de coordinación).
📊 Ejemplo de prueba de escalabilidad horizontal:

| Nodos | Throughput (RPS) | Speedup | Eficiencia | |-------|------------------|---------|-------------| | 1 | 1000 | 1.0x | 100% | | 2 | 1950 | 1.95x | 97.5% | | 4 | 3700 | 3.70x | 92.5% | | 8 | 6200 | 6.20x | 77.5% | | 16 | 8000 | 8.0x | 50% ← punto de eficiencia decreciente |

📌 Hasta 8 nodos, la eficiencia es aceptable (>75%). A partir de 16 nodos, añadir más recursos no es rentable.

✅ Buenas prácticas:
• 🔄 Probar con diferentes configuraciones de hardware/instancias.
• 📈 Simular aumentos graduales de carga y recursos (ej: 1, 2, 4, 8, 16 nodos).
• 🔍 Identificar cuellos de botella: base de datos, red, CPU, I/O, memoria.
• 📊 Usar herramientas de monitorización (Prometheus, Grafana, Datadog, New Relic).
• 🎯 Definir objetivos de escalabilidad: "El sistema debe ser capaz de manejar 10x el tráfico actual añadiendo nodos".
🔧 Herramientas para pruebas de escalabilidad:
• Apache JMeter / Gatling / k6: Para generar carga.
• Terraform / AWS CDK: Para orquestar infraestructura escalable.
• Kubernetes (K8s) + HPA (Horizontal Pod Autoscaler): Para probar escalado automático.
• Prometheus + Grafana: Para monitorizar métricas en tiempo real.
• Locust distribuido: Ejecutar agentes de carga desde múltiples máquinas.

📌 ¿Qué son las pruebas de confiabilidad?
Evalúan la capacidad del software para funcionar sin fallos durante un período de tiempo específico en condiciones normales de uso. Miden la probabilidad de que el sistema falle y el impacto de esos fallos.
📌 Procedimientos recomendados para crear aplicaciones confiables (Ian Sommerville):
• 🧠 Pensar en la confiabilidad desde el diseño inicial (no como un añadido).
• 📐 Diseñar con arquitectura flexible y tolerante a fallos (redundancia, recuperación).
• 🔍 Proporcionar supervisión y monitoreo continuo (alertas tempranas).
• 📋 Implementar un proceso de diseño de software de calidad (revisiones, estándares).
• 🔄 Validar procesos y entornos de forma regular (pruebas de aceptación del entorno).
• ⚠️ Implementar cambios con estudio previo (análisis de impacto, revisión de código).
• 📊 Portar atención al rendimiento y la estabilidad (medir y optimizar).
📊 Métricas de confiabilidad:
• MTBF (Mean Time Between Failures): Tiempo promedio entre fallos. MTBF alto = más confiable.
• MTTR (Mean Time To Repair/Recovery): Tiempo promedio de reparación. MTTR bajo = más resiliente.
• Disponibilidad (Availability): Porcentaje de tiempo que el sistema está operativo. Fórmula: MTBF / (MTBF + MTTR).
• Tasa de fallos (Failure Rate): Fallos por unidad de tiempo (ej: 0.01 fallos/hora).
• Número de fallos por demanda (POFOD): Probability of Failure on Demand (ej: 10^-5 significa 1 fallo cada 100,000 demandas).
📊 Ejemplo de cálculo de disponibilidad (Nueves):

| Disponibilidad | Tiempo de inactividad anual | Ejemplo | |----------------|-----------------------------|---------| | 99% (2 nueves) | 3.65 días (87.6 horas) | Aplicación interna no crítica | | 99.9% (3 nueves) | 8.76 horas | Servicio web típico | | 99.99% (4 nueves)| 52.56 minutos | Banca online, e-commerce | | 99.999% (5 nueves)| 5.26 minutos | Infraestructura crítica (ej: AWS) | | 99.9999% (6 nueves)| 31.5 segundos | Telecomunicaciones, satélites |
✅ Estrategias para mejorar la confiabilidad:
• 🔁 Redundancia: Servidores duplicados (active-passive o active-active), bases de datos en clúster.
• 🔄 Tolerancia a fallos: El sistema sigue funcionando (aunque degradado) si un componente falla.
• 📊 Monitorización proactiva: Alertas antes de que ocurra un fallo (ej: memory leak detectado temprano).
• 🧪 Pruebas de caos (Chaos Engineering): Netflix Simian Army, Gremlin, Chaos Monkey.
• 🔐 Circuit breakers: Patrón para evitar fallos en cascada (ej: Hystrix, Resilience4j).

🔒 Pruebas de Seguridad (Security Testing)

Las pruebas de seguridad identifican vulnerabilidades en el software que podrían ser explotadas por atacantes. Son críticas para proteger datos sensibles, mantener la integridad del sistema y cumplir con normativas.

📌 Tipos de pruebas de seguridad (SAST, DAST, IAST, RASP, SCA):

🛡️ SAST (Static Application Security Testing): Análisis del código fuente sin ejecutarlo. Detecta inyección SQL, XSS, buffer overflows, malas prácticas de codificación. Se ejecuta en el IDE o en CI/CD.
⚔️ DAST (Dynamic Application Security Testing): Pruebas de la aplicación en ejecución (caja negra). Detecta vulnerabilidades en APIs, autenticación, autorización, configuraciones inseguras.
🔬 IAST (Interactive Application Security Testing): Combina SAST y DAST, analiza en tiempo real durante pruebas funcionales. Más preciso y con menos falsos positivos.
🛡️ RASP (Runtime Application Self-Protection): Protege la aplicación en ejecución, detecta y bloquea ataques en tiempo real sin modificar el código.
📦 SCA (Software Composition Analysis): Analiza dependencias y librerías de terceros en busca de vulnerabilidades conocidas (CVEs). También verifica licencias.

📌 Diferencia clave - Pruebas de seguridad automatizadas vs Pentesting:
• Pruebas de seguridad (automatizadas): Se ejecutan frecuentemente (CI/CD), buscan vulnerabilidades conocidas con herramientas, cubren superficie amplia pero superficial.
• Pentesting (manual): Se realiza periódicamente (1-2 veces al año), simula ataques reales con ingeniería ofensiva, busca vulnerabilidades complejas y de lógica de negocio que herramientas automáticas no detectan.

🎨 Pruebas de Usabilidad (Usability Testing)

Las pruebas de usabilidad evalúan qué tan fácil, eficiente y satisfactorio es para los usuarios utilizar el software. Se centran en la experiencia de usuario (UX) y la interfaz (UI).

📌 ¿Qué se evalúa en usabilidad?
🎯 Efectividad: ¿Los usuarios pueden completar sus tareas? (tasa de éxito)
⚡ Eficiencia: ¿Cuánto tiempo y esfuerzo requieren? (tiempo de completitud)
😊 Satisfacción: ¿Qué tan contentos están con la experiencia? (encuestas)
📚 Aprendizaje: ¿Qué tan fácil es aprender a usar el sistema? (primer uso)
🔄 Memorabilidad: ¿Pueden recordar cómo usarlo después de un tiempo? (reutilización)
❌ Tasa de error: ¿Cuántos errores cometen los usuarios? (frecuencia y gravedad)

📊 Escala SUS (System Usability Scale):

📝 Puntuación SUS (0-100) - Interpretación:

• 90-100: 🌟 Excelente (mejor que el 99% de los sistemas)
• 80-89: 👍 Bueno (mejor que el 90% de los sistemas)
• 70-79: 📊 Aceptable (promedio)
• 60-69: ⚠️ Por debajo del promedio (necesita mejorar)
• < 60: ❌ Malo (requiere rediseño urgente)

Fórmula SUS: Para 10 preguntas (alternando positivas y negativas):
Puntuación = (suma de (respuestas_pares - 1) + (5 - respuestas_impares)) * 2.5
📌 Ejemplo de preguntas SUS (versión adaptada):
  1. Me gustaría usar este sistema frecuentemente.
  2. Encontré el sistema innecesariamente complejo. (R)
  3. Me pareció fácil usar el sistema.
  4. Necesitaría ayuda de un técnico para poder usar este sistema. (R)
  5. Encontré que las funciones del sistema están bien integradas.
  6. Había demasiada inconsistencia en el sistema. (R)
  7. Imagino que la mayoría de la gente aprendería a usar el sistema rápidamente.
  8. Encontré el sistema muy difícil de usar. (R)
  9. Me sentí muy confiado usando el sistema.
  10. Necesité aprender muchas cosas antes de poder usar el sistema. (R)
(R) = pregunta invertida (restar 5 - respuesta)

🧩 Pruebas Funcionales

Verifican que cada función del software cumpla con los requisitos especificados. Se basan en las entradas y salidas esperadas (caja negra), sin preocuparse por la estructura interna del código.

📌 Técnicas de diseño de pruebas funcionales (caja negra):

• Particiones de equivalencia: Dividir datos de entrada en clases equivalentes. Ejemplo: para un campo edad (1-100), las particiones son: inválido menor, válido, inválido mayor. Con 1 caso por partición basta.
• Análisis de valores límite: Probar los límites de los rangos. Ejemplo: edad mínima=1, máxima=100 → probar 0, 1, 2, 99, 100, 101.
• Tablas de decisión: Combinaciones de condiciones y acciones. Útil para lógica compleja con múltiples condiciones.
• Pruebas de transición de estados: Verificar cambios de estado del sistema (máquina de estados).
• Pruebas de casos de uso: Simular flujos completos de usuario (happy path y alternativos).
• Pruebas de escenarios (Scenario testing): Combinación de casos de uso que representan uso real.
📌 Ejemplo práctico - Particiones de equivalencia y valores límite:
Sistema: Formulario de edad (requiere edad entre 18 y 65 años inclusive).

- Válida: 18 a 65
- Inválida baja: 0 a 17
- Inválida alta: 66 a 120+

Valores límite:
- Límite inferior: 17, 18, 19
- Límite superior: 64, 65, 66

Casos de prueba mínimos: 17, 18, 19, 64, 65, 66

✅ Diferencias clave - Pruebas funcionales vs otras:
• Funcionales vs Unitarias: Las unitarias prueban componentes aislados; las funcionales prueban comportamiento visible para el usuario.
• Funcionales vs No funcionales: Las funcionales prueban QUÉ hace el sistema; las no funcionales prueban CÓMO lo hace (rendimiento, seguridad, usabilidad).
• Funcionales vs Regresión: Las funcionales se centran en nuevas funcionalidades; las de regresión verifican que no se rompió lo existente.

• Pruebas de bases de datos: DBUnit, SQLUnit, tSQLt.
• Pruebas BDD (Behavior-Driven Development): Cucumber, Behat, SpecFlow, JBehave.

📌 Estrategia de pruebas de compatibilidad:

2. Priorización: Principio 80/20: cubrir el 80% de los usuarios con el 20% de combinaciones.
3. Automatización: Pruebas funcionales automatizadas en navegadores principales (Chrome, Firefox).
4. Pruebas visuales: Capturas automáticas en múltiples resoluciones (Percy, BackstopJS, Chromatic).
5. Pruebas manuales: Exploratorias en combinaciones menos comunes (Safari en iOS, Edge en Windows).
6. CI/CD: Ejecutar suite de compatibilidad reducida en cada commit, y suite completa nightly.
⚠️ Problemas comunes de compatibilidad:
• CSS: Flexbox/Grid no soportado en navegadores antiguos, prefijos -webkit-, -moz-.

• Fuentes: Google Fonts puede no cargar en algunos entornos bloqueados.
• Cookies vs LocalStorage: IE11 tiene límites diferentes.
• Eventos táctiles: "click" vs "touchstart" en móviles.
• Web APIs: Geolocalización, notificaciones push, Service Workers no soportadas en todos los navegadores.

📌 ¿Qué son las pruebas de instalación?
Las pruebas de instalación aseguran que el software pueda ser instalado correctamente en los sistemas de los usuarios finales, que funcione después de la instalación y que se pueda desinstalar sin dejar archivos residuales o configuraciones dañinas. Son críticas para software empaquetado (installers) y despliegues en producción.
📌 Tipos de instalación a probar:

🔹 Instalación limpia (Clean install): Instalación en un sistema donde nunca ha estado el software antes. Verificar que se crean directorios, archivos, servicios, entradas de registro.
🔹 Actualización (Upgrade): Instalación sobre una versión anterior, conservando datos y configuraciones. Verificar que no se pierden datos ni configuraciones personalizadas.
🔹 Instalación silenciosa (Silent/Unattended): Instalación sin intervención del usuario (modo automatizado). Útil para despliegues masivos.
🔹 Instalación en red: Instalación desde un servidor remoto (UNC, HTTP).
🔹 Desinstalación completa: Eliminar todo rastro del software (archivos, claves de registro, carpetas). Verificar que no quedan archivos huérfanos.
🔹 Reparación/Modificación: Agregar o quitar componentes sin reinstalar completamente.
🔹 Instalación con espacio insuficiente: Simular disco lleno y verificar manejo de error.
🔹 Instalación con permisos insuficientes: Usuario sin privilegios de administrador.
📌 Aspectos críticos a verificar en instalación:
✅ Verificación de compatibilidad (SO, arquitectura, dependencias)
✅ Verificación de integridad del instalador (checksum, firma digital)
✅ Creación de directorios y archivos en las rutas correctas
✅ Creación de usuarios y grupos necesarios (si aplica)
✅ Asignación de permisos y privilegios apropiados
✅ Copia, desempaque y descompresión de archivos
✅ Compilación y enlace con bibliotecas requeridas
✅ Configuración inicial (parámetros, variables de entorno)
✅ Registro en sistema (Windows Registry, paquetes RPM/DEB, servicios systemd)
✅ Comportamiento con espacio insuficiente en disco
✅ Comportamiento si se cancela la instalación en mitad del proceso
✅ Comportamiento en diferentes idiomas / localizaciones
📌 Entornos de prueba recomendados:
• 🪟 Sistemas operativos: Windows 10/11 (32/64 bits), Windows Server, macOS (Intel/Apple Silicon), Linux (Ubuntu, CentOS, Debian).
• 📱 Móviles: iOS (últimas 2 versiones), Android (últimas 3 versiones).
• 🔧 Con y sin permisos de administrador: Verificar que funciona para usuarios estándar y admin.
• 🛡️ Con software conflictivo preinstalado: Antivirus (Windows Defender, McAfee), versiones anteriores del software, software que usa los mismos puertos.
• 💻 Máquinas virtuales limpias: Usar Vagrant, Docker, o snapshots de VM para pruebas repetibles.
• 🌐 Redes simuladas: Conexión lenta, intermitente o con proxy.
✅ Herramientas para automatizar pruebas de instalación:
• NSIS (Nullsoft Scriptable Install System): Para crear y probar instaladores en Windows.
• InstallShield / Advanced Installer: Herramientas profesionales para instaladores.
• Docker / Vagrant: Para crear entornos limpios y repetibles rápidamente.
• Packer: Para crear imágenes de máquinas base (AWS, VirtualBox, VMware).
• TestComplete / Ranorex: Automatización de la UI del instalador (hacer clic en botones).
• PowerShell scripts: Para automatizar la verificación post-instalación (servicios, claves de registro).
✅ Importancia de las pruebas de instalación:
Una mala instalación es la primera impresión que tiene el usuario del software. Si falla la instalación, el usuario nunca llegará a usar el producto, sin importar lo bueno que sea. Las pruebas de instalación son críticas para:
• 🚫 Evitar frustración en el usuario final (tasa de abandono).
• 📞 Reducir llamadas a soporte técnico (hasta un 30%).
• ✅ Asegurar que el software funcione desde el primer momento.
• 📋 Cumplir con requisitos de certificación (especialmente en software empresarial).
• 🔒 Seguridad: Evitar instalación de software no autorizado o con permisos incorrectos.

🔁 Pruebas de Recuperación (Recovery Testing)

Evalúan la capacidad del sistema para recuperarse tras un fallo (caída, corte de energía, error inesperado) y continuar funcionando correctamente. Son críticas para sistemas de alta disponibilidad y tolerancia a fallos.

📌 ¿Por qué son importantes?
En sistemas críticos (banca, salud, aeroespacial, emergencias, e-commerce), una mala recuperación puede tener consecuencias catastróficas: pérdida de vidas, pérdida económica millonaria, daño reputacional, o incumplimiento normativo.
📌 Metodología de pruebas de recuperación:

1. Planificación: Identificar escenarios de fallo críticos basados en análisis de riesgos.
2. Preparación: Configurar el entorno de prueba, hacer backup del estado inicial.
3. Ejecución del fallo: Forzar el fallo controlado en entorno de pruebas (no en producción).
4. Detección: Verificar que el sistema detecta el fallo (logs, métricas, alertas).
5. Recuperación: Comprobar si el sistema se recupera automática o manualmente.
6. Validación de datos: Asegurar que no hay pérdida ni corrupción de datos.
7. Medición: Calcular RTO y RPO reales comparados con objetivos.
8. Documentación: Registrar resultados, lecciones aprendidas, y acciones correctivas.
9. Automatización: Automatizar las pruebas más críticas (ej: Chaos Monkey).
📌 Tipos de fallos a simular:
💥 Caída del servidor (hardware/software)
⚡ Corte de energía (simulado con apagado abrupto)
🗄️ Fallo en base de datos (corrupción, desconexión, timeout)
🌐 Error en red o API externa (lentitud extrema, timeout, HTTP 500)
💾 Corrupción de datos en disco (archivos de configuración dañados)
🔄 Fallo en dependencias (cache Redis caído, cola RabbitMQ inaccesible)
🎯 Ataques de denegación de servicio (DDoS) simulado
📦 Fallo en contenedor/Pod de Kubernetes (kill pod)
☁️ Fallo de zona de disponibilidad (AZ) en cloud (simular caída de AWS us-east-1a)
🔐 Fallo de autenticación masivo (LDAP/Active Directory caído)
📌 Métricas clave en recuperación:

• RTO (Recovery Time Objective): Tiempo máximo tolerable de inactividad. Ejemplo: "Debemos recuperarnos en menos de 1 hora". Se mide desde el fallo hasta la recuperación total.
• RPO (Recovery Point Objective): Pérdida máxima tolerable de datos (en tiempo). Ejemplo: "Podemos perder hasta 15 minutos de datos". Define la frecuencia de backups.
• MTBF (Mean Time Between Failures): Tiempo promedio entre fallos. Mide la fiabilidad. MTBF alto = sistema más confiable.
• MTTR (Mean Time To Recovery): Tiempo promedio de recuperación. MTTR bajo = sistema más resiliente.
• Disponibilidad (Availability): Porcentaje de tiempo que el sistema está operativo. Fórmula: MTBF / (MTBF + MTTR).
• Recovery Point Actual (RPA): Lo que realmente se perdió en la prueba (debe ser ≤ RPO).
📊 Ejemplo de cálculo de disponibilidad con RTO y RPO:

Sistema: Servicio de pagos online
RTO objetivo: 30 minutos
RPO objetivo: 5 minutos

Backups: Cada 5 minutos (RPO cumplido)
Recuperación automática por failover: 25 minutos (RTO cumplido)

Resultado: ✅ Sistema cumple requisitos de disponibilidad.
✅ Buenas prácticas para pruebas de recuperación:
• 💾 Backups automáticos: Frecuencia definida por RPO (ej: cada 5 minutos para datos críticos).
• 🔁 Sistemas redundantes: Clusters activo-pasivo o activo-activo, réplicas de BD, balanceadores de carga.
• 📋 Planes de contingencia documentados: Procedimientos paso a paso para recuperación manual si falla la automática.
• 🧪 Pruebas periódicas de recuperación: Al menos cada 6 meses, o más frecuente para sistemas críticos (mensual).
• 📊 Monitorización y alertas tempranas: Prometheus, Grafana, Datadog, PagerDuty (alertas antes de que el fallo impacte a usuarios).
• 🎯 Chaos Engineering: Pruebas de caos en producción controlada (Netflix Simian Army, Gremlin, Chaos Mesh).
• 🔐 Aislar entorno de pruebas: No afectar a usuarios reales.
• 📝 Documentar y mejorar: Cada prueba de recuperación debe generar acciones para reducir MTTR.
📌 Ejemplo práctico - Prueba de recuperación de base de datos:
Escenario: PostgreSQL como base de datos principal.
RTO objetivo: 30 minutos.
RPO objetivo: 5 minutos.
Configuración: Backup cada 5 minutos, réplica en caliente (hot standby) en otra zona.

Prueba:
1. Se corrompe la base de datos principal intencionalmente (borrar archivos).
2. Sistema detecta fallo en 1 minuto (alerta).
3. Failover automático a réplica en 2 minutos.
4. Pérdida de datos: últimos backups (5 minutos). ✅ RPO cumplido.
5. Tiempo total de recuperación: 5 minutos. ✅ RTO cumplido.

Resultado: ✅ Prueba superada.

📄 Pruebas de Documentación (Documentation Testing)

Verifican que la documentación del software (manuales de usuario, guías de instalación, ayuda en línea, documentación técnica) sea clara, completa y precisa. La documentación es la "cara visible" del software para muchos usuarios.

📌 ¿Por qué es importante?
La documentación es la "cara visible" del software para muchos usuarios. Una documentación incorrecta, incompleta o desactualizada genera frustración, aumenta los costos de soporte (más tickets), reduce la satisfacción del cliente y puede incluso causar errores de uso críticos.
📌 Aspectos a evaluar en documentación:

• Exactitud: Los pasos descritos realmente funcionan en el software real. Verificar que las capturas de pantalla corresponden a la versión actual.
• Completitud: No faltan secciones, capítulos o instrucciones importantes. Todos los flujos principales están documentados.
• Claridad: El lenguaje es comprensible para el público objetivo (no es lo mismo documentación técnica para desarrolladores que manual de usuario final).
• Consistencia: No hay contradicciones entre diferentes documentos (manual vs ayuda online vs tooltips vs código).
• Utilidad: Realmente ayuda al usuario a resolver sus tareas (no es solo relleno o texto genérico).
• Actualización: La documentación refleja la versión actual del software (no contiene información obsoleta).
• Buscabilidad: El usuario puede encontrar fácilmente lo que necesita (índice, buscador, estructura lógica).
📌 Tipos de documentación a probar:
• 📖 Manuales de usuario: Funcionalidades, flujos, pantallas, ejemplos de uso.
• 🔧 Guías de instalación y configuración: Paso a paso para poner el software en marcha, requisitos de sistema.
• 💡 Ayuda en línea: Tooltips, FAQs, popups explicativos, archivos de ayuda (CHM, HTML).
• 👨‍💻 Documentación técnica para desarrolladores: API (endpoints, autenticación, ejemplos), arquitectura, guías de contribución, estándares de código.
• 🛠️ Documentación de administradores: Mantenimiento, backup, recuperación, monitorización, configuración de servidores.
• 🎬 Tutoriales y videos explicativos: Verificar que coinciden con la versión actual del software.
• 📋 Documentación de requisitos y diseño: Verificar que el software implementa lo especificado.
📌 Método de prueba (prueba de usuario de documentación):

1. Seleccionar participantes: Usuarios representativos del público objetivo (sin conocimiento previo del software).
2. Definir tareas concretas: Por ejemplo: "Instala el software", "Crea un informe de ventas", "Cambia tu contraseña", "Configura un backup automático".
3. Ejecutar prueba: Los usuarios realizan las tareas usando SOLO la documentación (sin ayuda del equipo, sin preguntar).
4. Observar y medir: ¿Pueden completar la tarea? ¿Cuánto tiempo tardan? ¿Cuántos errores cometen? ¿En qué paso se atascan?
5. Recoger feedback: Encuesta de satisfacción, preguntas abiertas sobre claridad y utilidad.
6. Analizar y mejorar: Identificar secciones problemáticas, reescribir, reorganizar, añadir ejemplos.
7. Iterar: Volver a probar con nuevos usuarios después de las mejoras.
📊 Métricas para documentación:
• Tasa de éxito: Porcentaje de usuarios que completan la tarea sin ayuda externa (objetivo >80%).
• Tiempo de completitud: Cuánto tiempo se tarda en seguir la guía (objetivo depende de la tarea).
• Tasa de error: Número de desviaciones o pasos incorrectos (objetivo <2 por tarea).
• Satisfacción (SUS adaptado): Encuesta específica para documentación (0-100).
• Tickets de soporte relacionados: Reducción esperada tras mejorar la documentación (ej: -30% de tickets).
• Tasa de abandono: Usuarios que abandonan la documentación sin completar la tarea.
✅ Herramientas de documentación recomendadas:
• Confluence (Atlassian): Wiki empresarial, fácil de usar, integración con Jira.
• ReadTheDocs / MkDocs: Generadores de documentación estática (muy usados en código abierto), gratuito.
• Docusaurus / VuePress: Modernos, basados en React/Vue, ideales para proyectos open source.
• Sphinx: Estándar en Python, genera PDF/HTML/EPUB, soporte para documentación de código.
• GitBook / Notion: Colaborativos y visuales, fáciles para equipos pequeños.
• Swagger / OpenAPI (para APIs): Documentación interactiva de APIs con pruebas integradas.
✅ Ejemplo práctico de prueba de documentación:
Escenario: Manual de instalación para una aplicación Windows.
Prueba: Un usuario nuevo sin experiencia previa sigue el manual paso a paso.
Problema detectado: El manual omite que se requieren permisos de administrador.
Impacto: El usuario no puede instalar, se frustra, abre ticket de soporte.
Corrección: Añadir advertencia al principio del manual: "Es necesario ejecutar el instalador como administrador".
Resultado: Después de la corrección, el 100% de los usuarios prueba completan la instalación sin errores.
