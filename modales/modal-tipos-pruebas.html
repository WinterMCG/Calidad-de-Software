🎬 Video: Pruebas de Software - Estrategias y Ejemplos

📌 Resumen: Las pruebas de software se clasifican en múltiples tipos según su objetivo (unitarias, integración, sistema, regresión, etc.) y su enfoque (caja negra, caja blanca, carga, seguridad, usabilidad). Aplicar la combinación adecuada garantiza la fiabilidad, el rendimiento y la satisfacción del usuario final.

🏔️ La Pirámide de pruebas (Mike Cohn)

La pirámide de pruebas es un concepto fundamental en ingeniería de software que recomienda la distribución óptima de los diferentes tipos de pruebas. Fue popularizada por Mike Cohn en su libro "Succeeding with Agile".

📌 ¿Qué nos enseña esta pirámide?

La pirámide de Mike Cohn es una guía para diseñar una estrategia de pruebas eficiente. Su forma indica dónde debemos poner el mayor esfuerzo de automatización:
  • 🔹 Base (Pruebas Unitarias): Deben ser la capa más grande. Son pruebas rápidas, aisladas y económicas que verifican funciones o métodos individuales. Una buena práctica es que constituyan alrededor del 70% del total de pruebas.
  • 🔹 Capa Media (Pruebas de Integración / API): Un número moderado. Verifican que los componentes interactúen correctamente entre sí y con servicios externos (bases de datos, APIs). Lo ideal es que representen cerca del 20%.
  • 🔹 Cúspide (Pruebas End-to-End / UI): Es la capa más pequeña. Simulan flujos completos de usuario a través de la interfaz gráfica. Son las más lentas, costosas y frágiles de mantener, por lo que se recomienda que sean solo un 5-10% del total.
🎯 Objetivo final: Invertir el esfuerzo donde más rendimiento obtenemos: muchas pruebas rápidas y baratas en la base, y pocas pruebas lentas y costosas en la cima. Esto acelera la retroalimentación al equipo y reduce drásticamente los costos de corrección.
⚠️ Antipatrón: La pirámide invertida (ice cream cone)

Cuando el equipo invierte excesivamente en pruebas End-to-End (UI) y descuida las pruebas unitarias, la distribución se invierte: muchas pruebas lentas y frágiles arriba y pocas pruebas rápidas abajo. Esto genera:
  • ❌ Ejecuciones de prueba muy lentas (minutos u horas).
  • ❌ Alta fragilidad: pequeños cambios en la interfaz rompen muchas pruebas.
  • ❌ Retroalimentación tardía para los desarrolladores.
  • ❌ Costos de mantenimiento elevados.
✅ Solución: Seguir la pirámide clásica: priorizar pruebas unitarias, luego integración, y solo unas pocas pruebas UI para validar flujos críticos.

📊 Distribución recomendada:

  • 70-80% Pruebas unitarias
  • 15-20% Pruebas de integración
  • 5-10% Pruebas E2E / Aceptación

💰 Costo relativo:

  • Unitarias: 1x
  • Integración: 5x
  • E2E / Aceptación: 20x

⚡ Velocidad de ejecución:

  • Unitarias: milisegundos
  • Integración: segundos
  • E2E / Aceptación: minutos
📌 Principios de la pirámide:
✅ Más pruebas abajo: Invertir en pruebas unitarias rápidas y baratas
✅ Menos pruebas arriba: Limitar pruebas end-to-end lentas y costosas
✅ Test early, test often: Probar temprano y frecuentemente
✅ Automatizar siempre que sea posible: Especialmente unitarias e integración
✅ Mantener la pirámide: Evitar la "pirámide invertida"

🎬 Video: Pruebas unitarias

🧪 Pruebas Unitarias (Unit Testing)

Las pruebas unitarias verifican el correcto funcionamiento de componentes individuales del software (funciones, métodos, clases) de forma aislada.

📌 Características de las pruebas unitarias:

✅ Alcance: Una función o método a la vez
✅ Responsable: Desarrollador
✅ Velocidad: Milisegundos
✅ Aislamiento: Sin dependencias externas (BD, API, red)
✅ Automatización: Fácil de automatizar
✅ Frecuencia: Cada vez que se compila/cambia el código

📝 Ejemplo de prueba unitaria (Python):

# Código a probar
def calcular_descuento(precio, porcentaje):
    if precio <= 0 or porcentaje < 0:
        return 0
    return precio * (porcentaje / 100)

# Prueba unitaria con pytest
def test_calcular_descuento():
    assert calcular_descuento(100, 10) == 10
    assert calcular_descuento(200, 25) == 50
    assert calcular_descuento(0, 10) == 0
    assert calcular_descuento(100, -5) == 0
    assert calcular_descuento(-50, 10) == 0

✅ Beneficios de las pruebas unitarias:
• Detectan errores temprano en el desarrollo
• Facilitan el refactorización (cambiar código con confianza)
• Sirven como documentación viva del código
• Reducen el tiempo de debugging
• Mejoran el diseño del código (forzan a escribir código testeable)

❌ Limitaciones:
• No detectan errores de integración entre módulos
• No verifican el sistema completo
• Pueden ser frágiles si el código cambia mucho
• No reemplazan las pruebas de sistema

🎬 Video: Pruebas de integración

🔗 Pruebas de Integración (Integration Testing)

Las pruebas de integración verifican que los diferentes módulos o componentes del sistema funcionen correctamente cuando se combinan.

📌 Tipos de integración:

🔹 Integración ascendente (Bottom-Up):
  ✓ Se prueban primero los módulos de bajo nivel
  ✓ Luego se integran con módulos de alto nivel
  ✓ Ejemplo: Probar primero el acceso a datos, luego la lógica de negocio

🔹 Integración descendente (Top-Down):
  ✓ Se prueban primero los módulos de alto nivel
  ✓ Se usan "stubs" para simular módulos de bajo nivel
  ✓ Ejemplo: Probar la interfaz de usuario simulando el backend

🔹 Integración big bang:
  ✓ Se integran todos los módulos a la vez
  ✓ Alto riesgo, difícil de depurar
  ✓ ❌ No recomendada para sistemas grandes

🔹 Integración incremental:
  ✓ Se integran módulos de uno en uno o en pequeños grupos
  ✓ Más fácil de localizar errores
  ✓ ✅ Recomendada

📝 Ejemplo de prueba de integración (API):

// Prueba de integración de API con Supertest (Node.js)
const request = require('supertest');
const app = require('../app');

describe('POST /api/usuarios', () => {
    test('debe crear un usuario válido', async () => {
        const nuevoUsuario = {
            nombre: 'Juan Pérez',
            email: 'juan@ejemplo.com',
            password: '123456'
        };
        
        const response = await request(app)
            .post('/api/usuarios')
            .send(nuevoUsuario);
            
        expect(response.statusCode).toBe(201);
        expect(response.body).toHaveProperty('id');
        expect(response.body.email).toBe('juan@ejemplo.com');
    });
});

🎯 Enfoques para pruebas de integración:

EnfoqueDescripciónVentajasDesventajas

Top-DownDe arriba hacia abajoPrueba lógica principal tempranoRequiere stubs

SándwichCombinación Top-Down + Bottom-UpBalanceadoMás complejo de coordinar
✅ Beneficios de las pruebas de integración:
• Detectan errores en las interfaces entre módulos
• Verifican el flujo de datos entre componentes
• Prueban la comunicación con sistemas externos (BD, APIs)
• Aumentan la confianza en el sistema completo

❌ Desafíos:
• Configuración más compleja (bases de datos reales, servicios)
• Pueden ser lentas (segundos, no milisegundos)
• Dependencias externas pueden fallar (no culpa del código)

🎬 Video: Pruebas de sistema

🌐 Pruebas de Sistema (System Testing)

Las pruebas de sistema evalúan el software completo e integrado en un entorno similar al de producción. Verifican que el sistema cumpla con todos los requisitos especificados.

📌 Tipos de pruebas de sistema:

🧪 Pruebas funcionales: Verifican que todas las funcionalidades cumplan los requisitos
⚡ Pruebas de rendimiento: Evalúan tiempos de respuesta, consumo de recursos
🔒 Pruebas de seguridad: Verifican la protección contra amenazas
🎨 Pruebas de usabilidad: Evalúan la facilidad de uso
🔄 Pruebas de compatibilidad: Verifican funcionamiento en diferentes entornos
🔧 Pruebas de recuperación: Evalúan la capacidad de recuperarse de fallos
🌍 Pruebas de localización: Verifican adaptación a diferentes idiomas/regiones
📱 Pruebas multiplataforma: Verifican funcionamiento en diferentes dispositivos

📊 Comparativa: Sistema vs Integración vs Unitarias

✅ Beneficios de las pruebas de sistema:
• Verifican que el sistema cumpla con todos los requisitos
• Detectan problemas de integración final
• Simulan el uso real del sistema
• Son la última línea de defensa antes del despliegue

❌ Limitaciones:
• Costosas y lentas de ejecutar
• Requieren un entorno de prueba completo
• Difíciles de automatizar completamente
• Los errores son más costosos de corregir en esta fase

🎬 Video: Pruebas de aceptación

✅ Pruebas de Aceptación (Acceptance Testing)

Las pruebas de aceptación son realizadas por el cliente o usuario final para determinar si el software está listo para ser entregado y cumple con sus necesidades.

🧪 Pruebas alfa (Alpha Testing)

Realizadas internamente por el equipo de prueba en el entorno de desarrollo, antes de liberar al cliente.

Características: Entorno controlado, equipo interno, detecta bugs obvios.

🌍 Pruebas beta (Beta Testing)

Realizadas por un grupo selecto de usuarios reales en sus propios entornos, antes del lanzamiento oficial.

Características: Entorno real, feedback de usuarios, detecta problemas de usabilidad.

📝 Ejemplo de criterios de aceptación (Gherkin - BDD):

Característica: Inicio de sesión de usuario
  Como usuario registrado
  Quiero poder iniciar sesión en el sistema
  Para acceder a mis datos personales

  Escenario: Inicio de sesión exitoso
    Dado que soy un usuario registrado con correo "juan@ejemplo.com" y contraseña "123456"
    Cuando ingreso mi correo y contraseña correctos
    Y hago clic en "Iniciar sesión"
    Entonces debería ver mi panel de control
    Y debería ver un mensaje "Bienvenido Juan"

  Escenario: Inicio de sesión con contraseña incorrecta
    Dado que soy un usuario registrado
    Cuando ingreso mi correo correcto y una contraseña incorrecta
    Y hago clic en "Iniciar sesión"
    Entonces debería ver un mensaje "Correo o contraseña incorrectos"
    Y debería permanecer en la página de inicio de sesión
✅ Criterios de aceptación (características SMART):
• Specific (Específico): Sin ambigüedades
• Measurable (Medible): Se puede verificar
• Achievable (Alcanzable): Realista técnicamente
• Relevant (Relevante): Aporta valor
• Time-bound (Con plazo): Tiene fecha límite (si aplica)

🎬 Video: Pruebas de regresión

🔄 Pruebas de Regresión (Regression Testing)

Las pruebas de regresión verifican que los cambios recientes (nuevas funcionalidades, correcciones de bugs) no hayan roto las funcionalidades existentes.

📌 Cuándo ejecutar pruebas de regresión:

🔄 Después de cada cambio en el código (idealmente en CI/CD)
🔄 Antes de cada lanzamiento o despliegue
🔄 Cuando se corrigen bugs (verificar que la corrección no rompa algo más)
🔄 Al agregar nuevas funcionalidades
🔄 Al refactorizar código
🔄 Al actualizar dependencias o librerías

📊 Estrategias para pruebas de regresión:

EstrategiaDescripciónVentajasDesventajas
Regresión completaEjecutar todas las pruebasMáxima cobertura, seguroMuy lento, costoso
Regresión selectivaEjecutar solo pruebas relacionadasRápido, eficienteRiesgo de omitir áreas afectadas
Regresión priorizadaEjecutar pruebas por prioridadEquilibrio entre tiempo y coberturaRequiere definir prioridades
Regresión híbridaCombinación de estrategiasFlexible, adaptableMás compleja de gestionar
✅ Mejores prácticas para regresión:
• 🤖 Automatizar las pruebas de regresión tanto como sea posible
• 📦 Mantener un conjunto de pruebas "humo" rápidas para ejecutar siempre
• 🎯 Identificar y priorizar las pruebas más críticas
• 🔧 Usar herramientas de CI/CD (Jenkins, GitHub Actions, GitLab CI)
• 📊 Monitorear el tiempo de ejecución y optimizar
• 🔄 Ejecutar regresión en cada commit (al menos el conjunto rápido)
• 📝 Documentar los resultados y tendencias

🎬 Video: Pruebas de humo

💨 Pruebas de Humo (Smoke Testing)

Las pruebas de humo son un conjunto de pruebas rápidas y superficiales que verifican que las funcionalidades más críticas del sistema funcionan antes de realizar pruebas más profundas.

📌 Origen del nombre:
Proviene del hardware: cuando se encendía un dispositivo electrónico, si salía humo significaba que había un problema grave. Si no salía humo, se podía proceder a probar más a fondo.

🎯 ¿Qué probar en pruebas de humo?

  • 🚀 El sistema inicia correctamente
  • 🔐 Las páginas principales cargan (login, dashboard)
  • 🔄 Los flujos críticos funcionan (registro, compra, pago)
  • 🔌 Las conexiones a servicios externos funcionan (BD, APIs)
  • 📱 Las pantallas principales en dispositivos móviles cargan
  • ⚡ La respuesta no es extremadamente lenta
✅ Ventajas:
• Rápidas (minutos, no horas)
• Detectan problemas críticos temprano
• Ahorran tiempo (no se prueban builds rotas en profundidad)
• Fáciles de automatizar
• Mejoran la confianza en el build
❌ Limitaciones:
• No detectan errores sutiles o específicos
• No reemplazan las pruebas funcionales completas
• Solo verifican lo más básico

📝 Ejemplo de suite de pruebas de humo:

✅ Página de login carga (status 200)
✅ Usuario puede iniciar sesión con credenciales válidas
✅ Dashboard carga después del login
✅ Listado de productos carga
✅ Se puede agregar un producto al carrito
✅ Carrito muestra el producto agregado
✅ Página de checkout carga
✅ Usuario puede cerrar sesión
⚠️  Todas las pruebas de humo PASARON → Se puede proceder a pruebas completas

⚡ Pruebas de Carga y Estrés

Evalúan el comportamiento del sistema bajo condiciones normales y extremas de uso (muchos usuarios concurrentes, grandes volúmenes de datos).

📊 Pruebas de carga (Load Testing)

Simulan cargas esperadas de usuarios o transacciones para verificar que el sistema responde dentro de los límites aceptables.

Objetivos: Tiempo de respuesta, throughput, uso de CPU/memoria, estabilidad bajo carga normal.

💥 Pruebas de estrés (Stress Testing)

Llevan el sistema más allá de sus límites para ver cómo falla y si se recupera adecuadamente.

Objetivos: Punto de quiebre, comportamiento durante fallos, capacidad de recuperación.

🔧 Herramientas para pruebas de carga:

📌 Ejemplo de script JMeter (concepto):

✅ Métricas clave en pruebas de carga:
• ⏱️ Tiempo de respuesta promedio, p90, p95, p99
• 📊 Throughput (peticiones por segundo)
• 💾 Uso de CPU, memoria, disco, red
• ❌ Tasa de errores (timeouts, 500, etc.)
• 👥 Número máximo de usuarios concurrentes soportados
• 🔄 Tiempo de recuperación tras sobrecarga

🎬 Video: Pruebas de seguridad

🔒 Pruebas de Seguridad (Security Testing)

Las pruebas de seguridad identifican vulnerabilidades en el software que podrían ser explotadas por atacantes.

🛡️ Análisis SAST

Static Application Security Testing - Análisis del código fuente sin ejecutarlo.

Detección: Inyección SQL, XSS, buffer overflows, malas prácticas.

Herramientas: SonarQube, Checkmarx, Fortify.

⚔️ Análisis DAST

Dynamic Application Security Testing - Pruebas de la aplicación en ejecución.

Detección: Vulnerabilidades en APIs, autenticación, autorización.

Herramientas: OWASP ZAP, Burp Suite, Acunetix.

🔐 Pruebas de penetración

Simulación controlada de ataques reales por expertos en seguridad.

Enfoque: Manual y automatizado, busca explotar vulnerabilidades.

Realizadas por: Ethical hackers, equipos de Red Team.

📦 Análisis SCA

Software Composition Analysis - Análisis de dependencias y librerías de terceros.

Detección: Vulnerabilidades conocidas en paquetes, licencias.

Herramientas: OWASP Dependency-Check, Snyk.

• 🔐 Incluir pruebas de seguridad en CI/CD
• 📊 Realizar análisis SAST/DAST regularmente

🎨 Pruebas de Usabilidad (Usability Testing)

Las pruebas de usabilidad evalúan qué tan fácil, eficiente y satisfactorio es para los usuarios utilizar el software.

📌 ¿Qué se evalúa en usabilidad?

🎯 Efectividad: ¿Los usuarios pueden completar sus tareas?
⚡ Eficiencia: ¿Cuánto tiempo y esfuerzo requieren?
😊 Satisfacción: ¿Qué tan contentos están con la experiencia?
📚 Aprendizaje: ¿Qué tan fácil es aprender a usar el sistema?
🔄 Memorabilidad: ¿Pueden recordar cómo usarlo después de un tiempo?
❌ Tasa de error: ¿Cuántos errores cometen los usuarios?

📊 Escala SUS (System Usability Scale):

📝 Puntuación SUS (0-100):

• 90-100: 🌟 Excelente, mejor que el 99% de los sistemas
• 80-89: 👍 Bueno, mejor que el 90% de los sistemas
• 70-79: 📊 Aceptable, promedio
• 60-69: ⚠️ Por debajo del promedio, necesita mejorar
• < 60: ❌ Malo, requiere rediseño urgente

Fórmula SUS:
Para 10 preguntas (alternando positivas y negativas):
Puntuación = (suma de (respuestas_pares - 1) + (5 - respuestas_impares)) * 2.5

🎯 Métodos comunes de pruebas de usabilidad:

MétodoDescripciónCuándo usarlo

Remoto no moderadoUsuarios completan tareas por su cuentaCuando se necesitan muchas respuestas
Pruebas A/BComparar dos versiones del diseñoPara decidir entre alternativas
Análisis de eye-trackingMide dónde miran los usuariosPara optimizar layout visual
Encuestas (SUS, UMUX)Cuestionarios estandarizadosPara mediciones cuantitativas
✅ Herramientas para pruebas de usabilidad:
• Hotjar / FullStory: Mapas de calor, grabaciones de sesiones
• UserTesting / Maze: Pruebas remotas con usuarios reales
• Lighthouse / PageSpeed: Análisis de experiencia de usuario web
• Google Analytics: Métricas de comportamiento (tasa de rebote, tiempo en página)
• Crazy Egg: Mapas de calor y seguimiento de clics

🧩 Pruebas Funcionales

Verifican que cada función del software cumpla con los requisitos especificados. Se basan en las entradas y salidas esperadas, sin preocuparse por la estructura interna del código.

📌 Características:
• Se enfocan en el comportamiento observable.
• Utilizan técnicas de caja negra (particiones de equivalencia, valores límite, tablas de decisión).
• Son esenciales para validar que el software hace lo que debe hacer.
• Se basan en casos de prueba derivados de los requisitos funcionales.
✅ Ejemplo práctico: Probar que un formulario de login valida correctamente el correo y la contraseña, mostrando el mensaje de error apropiado cuando son incorrectos.

🎬 Video: Pruebas de compatibilidad

🔌 Pruebas de Compatibilidad

Verifican que el software funcione correctamente en diferentes entornos, navegadores, dispositivos y sistemas operativos.

📌 Tipos de compatibilidad:
• Navegadores (Chrome, Firefox, Safari, Edge)
• Sistemas operativos (Windows, macOS, Linux, iOS, Android)
• Versiones anteriores (backward compatibility)
• Resoluciones de pantalla y dispositivos móviles
• Integración con otros sistemas y APIs
✅ Herramientas comunes: BrowserStack, Sauce Labs, LambdaTest.

🎬 Video: Pruebas de instalación

💿 Pruebas de Instalación

Verifican que el proceso de instalación, actualización y desinstalación del software se realice correctamente en los entornos destino.

📌 Aspectos a probar:
• Instalación limpia (primera vez)
• Actualización desde versiones anteriores
• Desinstalación completa (sin archivos residuales)
• Instalación silenciosa / no interactiva
• Comportamiento en diferentes configuraciones de hardware y SO
• Permisos y privilegios necesarios
✅ Importancia: Una mala instalación puede impedir que el usuario utilice el software, incluso si el código es perfecto.

🔁 Pruebas de Recuperación

Evalúan la capacidad del sistema para recuperarse tras un fallo (caída, corte de energía, error inesperado) y continuar funcionando correctamente.

📌 Metodología:
1. Se fuerza un fallo controlado (sistema, red, base de datos).
2. Se verifica si el sistema puede recuperarse.
3. Se comprueba si la recuperación es automática o requiere intervención manual.
4. Se valida que los datos no se hayan perdido ni corrompido.
✅ ¿Por qué son importantes? En sistemas críticos (banca, salud, aeroespacial), una mala recuperación puede tener consecuencias catastróficas.

🎬 Video: Documentación en proyectos de software

📄 Pruebas de Documentación

Verifican que la documentación del software (manuales de usuario, guías de instalación, ayuda en línea) sea clara, completa y precisa.

📌 Aspectos a evaluar:
• Exactitud: los pasos descritos realmente funcionan.
• Completitud: no faltan secciones ni instrucciones.
• Claridad: el lenguaje es comprensible para el público objetivo.
• Consistencia: no hay contradicciones entre diferentes documentos.
• Utilidad: realmente ayuda al usuario a resolver sus tareas.
✅ Ejemplo práctico: Probar que el manual de instalación describe correctamente todos los pasos y que un usuario nuevo puede seguir la guía sin problemas.
