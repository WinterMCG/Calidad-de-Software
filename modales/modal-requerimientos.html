Proceso de obtención de requisitos (Sommerville)

La ingeniería de requisitos es una de las fases más críticas del desarrollo de software. Un error en esta fase puede costar hasta 100 veces más corregirlo en producción.

🎬 Video: Principios de la Ingeniería de Requerimientos

📋 Las 4 etapas fundamentales:

🔍 1. Estudio de viabilidad
  ✓ ¿Es técnicamente posible?
  ✓ ¿Es económicamente viable?
  ✓ ¿Cumple con requisitos legales y regulatorios?
  ✓ ¿Se puede implementar en el plazo establecido?

🗣️ 2. Obtención y análisis
  ✓ Entrevistas con stakeholders
  ✓ Talleres de requisitos
  ✓ Observación etnográfica
  ✓ Análisis de documentos existentes
  ✓ Prototipado rápido

📝 3. Especificación
  ✓ Redactar requisitos claros y sin ambigüedades
  ✓ Crear documento SRS (Software Requirements Specification)
  ✓ Usar plantillas estandarizadas (IEEE 830)
  ✓ Incluir diagramas y modelos

✅ 4. Validación
  ✓ Revisar con el cliente que los requisitos sean correctos
  ✓ Verificar que sean completos y consistentes
  ✓ Asegurar que sean realistas y alcanzables
  ✓ Obtener aprobación formal

⚠️ Error común: Saltarse la validación es uno de los errores más frecuentes y costosos. Luego el software no sirve y hay que rehacer, generando retrasos y sobrecostos.

📊 Estadísticas importantes:

  • El 40-50% de los defectos en software se originan en requisitos mal definidos
  • Invertir tiempo en una buena especificación puede ahorrar hasta un 80% del costo total
  • Los proyectos con requisitos bien gestionados tienen 2.5 veces más probabilidad de éxito

Requisitos Funcionales y No Funcionales

Requisitos Funcionales

Describen comportamientos específicos que el sistema debe ejecutar. Responden a la pregunta: "¿Qué debe hacer el sistema?"

Características:

  • Describen acciones concretas
  • Son verificables mediante pruebas
  • Definen entradas y salidas esperadas
  • Son específicos del dominio del problema

Ejemplos:

  • ✓ "El sistema debe permitir registrar pacientes con nombre, teléfono y correo"
  • ✓ "El sistema debe enviar un correo de confirmación al registrarse"
  • ✓ "El sistema debe generar un reporte de ventas mensual en PDF"
  • ✓ "El sistema debe validar que el usuario existe antes de iniciar sesión"
  • ✓ "El sistema debe calcular el total de una compra incluyendo impuestos"

Requisitos No Funcionales

Describen cualidades o restricciones del sistema. Responden a la pregunta: "¿Cómo debe ser el sistema?"

Categorías principales:

  • Rendimiento: tiempos de respuesta, throughput
  • Seguridad: confidencialidad, integridad, disponibilidad
  • Usabilidad: facilidad de uso, curva de aprendizaje
  • Confiabilidad: disponibilidad, MTBF, tolerancia a fallos
  • Mantenibilidad: modularidad, capacidad de prueba
  • Portabilidad: compatibilidad entre plataformas
  • Escalabilidad: capacidad de crecer con la demanda
  • Interoperabilidad: integración con otros sistemas

Ejemplos:

  • ⚡ "La consulta debe resolverse en menos de 2 segundos" (rendimiento)
  • 🔒 "Solo el administrador puede eliminar citas" (seguridad)
  • 💻 "El sistema debe funcionar en Windows 10 y Linux" (portabilidad)
  • 📱 "La interfaz debe ser responsive en dispositivos móviles" (usabilidad)
  • 🔄 "El sistema debe estar disponible el 99.9% del tiempo" (confiabilidad)
📊 Diferencia clave:

Si un requisito funcional NO se cumple → el sistema no hace algo que debería hacer.
Si un requisito no funcional NO se cumple → el sistema hace lo que debe, pero mal (lento, inseguro, difícil de usar).

Los requisitos no funcionales son igual de importantes que los funcionales, pero a menudo se olvidan o se posponen. Una aplicación que funciona pero es extremadamente lenta o insegura es inservible.

📌 Características de un buen requisito (SMART):

  • Specific (Específico): No ambiguo, claro y preciso
  • Measurable (Medible): Se puede cuantificar o verificar
  • Achievable (Alcanzable): Técnicamente factible
  • Relevant (Relevante): Aporta valor al negocio
  • Time-bound (Temporal): Tiene plazo definido (si aplica)

📚 Profundización en Ingeniería de Requerimientos

1. Técnicas de elicitación de requisitos

Existen múltiples técnicas para obtener requisitos de los stakeholders:

  • 📋 Entrevistas: Conversaciones uno a uno con stakeholders. Pueden ser estructuradas o no estructuradas.
  • 👥 Talleres (JAD - Joint Application Development): Sesiones grupales donde stakeholders y desarrolladores colaboran.
  • 🔍 Observación etnográfica: Observar a los usuarios en su entorno de trabajo real.
  • 📄 Análisis de documentos: Revisar documentación existente (manuales, formularios, reportes).
  • 🎨 Prototipado: Crear versiones tempranas del sistema para obtener retroalimentación.
  • 📊 Cuestionarios y encuestas: Útiles para grandes grupos de usuarios.
  • 🧠 Brainstorming: Generación creativa de ideas en grupo.
  • 📖 Historias de usuario: Descripciones cortas desde la perspectiva del usuario ("Como [rol], quiero [acción], para [beneficio]").

2. Documento SRS según IEEE 830

IEEE 830 define la estructura estándar para un documento de especificación de requisitos:

📑 Estructura de un SRS según IEEE 830:

1. Introducción
  1.1 Propósito
  1.2 Alcance
  1.3 Definiciones y acrónimos
  1.4 Referencias
  1.5 Visión general

2. Descripción general
  2.1 Perspectiva del producto
  2.2 Funciones del producto
  2.3 Características de los usuarios
  2.4 Restricciones
  2.5 Suposiciones y dependencias

3. Requisitos específicos
  3.1 Interfaces externas
  3.2 Funciones
  3.3 Requisitos de rendimiento
  3.4 Restricciones de diseño
  3.5 Atributos de software (confiabilidad, seguridad, mantenibilidad)
  3.6 Otros requisitos

4. Apéndices

3. Gestión de cambios en requisitos

Los requisitos cambian durante el proyecto. Es fundamental tener un proceso de gestión de cambios:

  • Solicitud de cambio: Cualquier stakeholder puede solicitar un cambio
  • Análisis de impacto: Evaluar cómo afecta el cambio al costo, tiempo y alcance
  • Comité de control de cambios: Grupo que aprueba o rechaza cambios
  • Implementación: Ejecutar el cambio aprobado
  • Actualización de trazabilidad: Mantener la matriz de trazabilidad actualizada
  • Comunicación: Notificar a todos los interesados sobre el cambio
