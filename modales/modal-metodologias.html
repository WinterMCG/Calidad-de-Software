Metodologías de Desarrollo de Software

La elección de la metodología adecuada es fundamental para el éxito de un proyecto. A continuación se presentan las principales metodologías, sus ventajas, desventajas y cuándo aplicarlas.

🎬 Introducción: ¿Qué son las metodologías de software?
🎬 Modelos y metodologías de desarrollo (completo)

📊 ¿Cómo elegir la metodología adecuada?

📌 Responde estas preguntas para tomar la decisión:

❓ ¿Los requisitos están 100% claros y no van a cambiar?
  ✅ Sí → Cascada, Modelo en V o Incremental
  ❌ No → Scrum, XP o Espiral

❓ ¿El cliente quiere ver resultados rápido?
  ✅ Sí → Scrum (sprints cortos) o Prototipos
  ❌ No → Cascada

❓ ¿El equipo recibe muchas solicitudes urgentes e impredecibles?
  ✅ Sí → Kanban
  ❌ No → Scrum o Cascada

❓ ¿Es un proyecto pequeño y de corta duración (menos de 3 meses)?
  ✅ Sí → Cascada
  ❌ No → Scrum

❓ ¿Es un sistema crítico que requiere mucha documentación y trazabilidad?
  ✅ Sí → Cascada, Modelo en V o Espiral
  ❌ No → Scrum

❓ ¿La calidad del código es la máxima prioridad?
  ✅ Sí → XP (pair programming, TDD)
  ❌ No → Scrum o Cascada

❓ ¿Es un proyecto empresarial grande con equipos distribuidos?
  ✅ Sí → RUP
  ❌ No → Scrum o Cascada

💧 Cascada (Waterfall) - Metodología Tradicional

🎬 Explicación del modelo en cascada
📊 Fases del modelo en cascada:

┌─────────────────────────────────────────────────────────────────┐
│ 1. REQUISITOS │
│ (Análisis, entrevistas, documentación SRS) │
└─────────────────────────────────────┬───────────────────────────┘
▼
┌─────────────────────────────────────────────────────────────────┐
│ 2. DISEÑO │
│ (Arquitectura, BD, interfaces, mockups) │
└─────────────────────────────────────┬───────────────────────────┘
▼
┌─────────────────────────────────────────────────────────────────┐
│ 3. IMPLEMENTACIÓN │
│ (Codificación, pruebas unitarias) │
└─────────────────────────────────────┬───────────────────────────┘
▼
┌─────────────────────────────────────────────────────────────────┐
│ 4. PRUEBAS │
│ (Integración, sistema, aceptación, regresión) │
└─────────────────────────────────────┬───────────────────────────┘
▼
┌─────────────────────────────────────────────────────────────────┐
│ 5. MANTENIMIENTO │
│ (Correcciones, mejoras, soporte técnico) │
└─────────────────────────────────────────────────────────────────┘

✅ Ventajas

  • Simple y fácil de entender
  • Hitos y entregables claros por fase
  • Documentación exhaustiva desde el inicio
  • Buena para proyectos con requisitos estables
  • Facilita la planificación de recursos
  • Ideal para equipos grandes y distribuidos

❌ Desventajas

  • No tolera cambios (muy costoso volver atrás)
  • El cliente ve el producto hasta el final
  • Riesgo de que los requisitos cambien durante el desarrollo
  • Los errores se descubren tarde (en pruebas)
  • Puede generar largos tiempos de espera
📌 ¿Cuándo usar Cascada?
• Requisitos claros, estables y bien documentados
• Proyectos pequeños o medianos (< 6 meses)
• Tecnologías conocidas por el equipo
• Cliente no necesita ver avances frecuentes
• Proyectos con regulaciones estrictas (gubernamentales, médicos)
• Equipo distribuido que necesita documentación detallada

🔄 Scrum - Metodología Ágil

🎬 Scrum explicado en 6 minutos
📊 Estructura de Scrum:

    Sprint Planning ──► Sprint (1-4 semanas) ──► Sprint Review
          ▲                                         │
          │                                         ▼
    Product Backlog                          Sprint Retrospective
    (lista de prioridades)                          │
          ▲                                         │
          │                                         ▼
    Product Owner ──────────────────────► Incremento entregable

👥 Roles en Scrum

  • Product Owner: Define prioridades, gestiona el backlog
  • Scrum Master: Facilita el proceso, elimina impedimentos
  • Equipo de desarrollo: Autoorganizado, multifuncional (3-9 miembros)

📦 Artefactos de Scrum

  • Product Backlog: Lista priorizada de funcionalidades
  • Sprint Backlog: Tareas seleccionadas para el sprint
  • Incremento: Versión funcional al final del sprint

⏰ Eventos de Scrum

  • Sprint Planning: Planificar el sprint (máx 8 horas)
  • Daily Scrum: Reunión diaria de 15 minutos
  • Sprint Review: Demostrar lo construido (máx 4 horas)
  • Sprint Retrospective: Mejorar el proceso (máx 3 horas)

✅ Ventajas

  • Adaptabilidad a cambios
  • Entrega temprana de valor al cliente
  • Visibilidad y transparencia
  • Mejora continua (retrospectivas)
  • Alta motivación del equipo (autogestión)
  • Reducción de riesgos

❌ Desventajas

  • Requiere compromiso total del equipo
  • El cliente debe estar disponible frecuentemente
  • Menor documentación (puede ser problema para equipos grandes)
  • Puede derivar en "scope creep" (más funcionalidades de lo planeado)
  • Requiere experiencia en estimación ágil
📌 ¿Cuándo usar Scrum?
• Requisitos cambiantes o inciertos
• Cliente involucrado y disponible
• Equipo pequeño a mediano (3-9 personas)
• Proyectos donde la velocidad de entrega es prioritaria
• Equipo con capacidad de autoorganización
• Productos innovadores o con alta incertidumbre

📋 Kanban - Flujo Continuo

🎬 Metodología Kanban explicada
📊 Tablero Kanban básico:

┌─────────────────┬─────────────────┬─────────────────┬─────────────────┐
│ POR HACER │ EN PROGRESO │ EN REVISIÓN │ HECHO │
│ (Backlog) │ (WIP: 3) │ (WIP: 2) │ │
├─────────────────┼─────────────────┼─────────────────┼─────────────────┤
│ • Tarea 1 │ • Tarea 2 │ • Tarea 3 │ ✓ Tarea 4 │
│ • Tarea 5 │ • Tarea 6 │ │ ✓ Tarea 7 │
│ • Tarea 8 │ • Tarea 9 │ │ ✓ Tarea 10 │
│ • Tarea 11 │ │ │ │
└─────────────────┴─────────────────┴─────────────────┴─────────────────┘
WIP = Work In Progress (trabajo en progreso)

✅ Ventajas

  • Visualización clara del flujo de trabajo
  • Límites de WIP evitan cuellos de botella
  • Flexibilidad para priorizar tareas
  • No requiere sprints fijos
  • Reduce el tiempo de ciclo
  • Ideal para equipos de soporte/mantenimiento

❌ Desventajas

  • No tiene iteraciones fijas (puede faltar planificación a largo plazo)
  • Puede generar procrastinación si no se gestiona bien
  • Requiere disciplina para respetar límites de WIP
  • Menor previsibilidad en fechas de entrega
📌 ¿Cuándo usar Kanban?
• Equipos de soporte técnico o mantenimiento
• Proyectos con tareas heterogéneas y urgentes
• Equipos que reciben solicitudes impredecibles
• Cuando se quiere mejorar el flujo existente sin cambios disruptivos
• Proyectos donde la prioridad cambia constantemente
• Equipos que ya tienen un proceso pero quieren visualizarlo

⚡ XP (Extreme Programming)

🎬 Programación Extrema (XP): prácticas y ciclo de vida
📊 Prácticas clave de XP:

🔄 Programación en pares (Pair Programming): Dos desarrolladores trabajan juntos en una misma estación
🧪 TDD (Test-Driven Development): Escribir pruebas antes del código
🔁 Integración continua: Integrar código varias veces al día
📝 Refactorización: Mejorar el código sin cambiar funcionalidad
🗣️ Cliente en sitio: Un cliente real disponible todo el tiempo
📊 Velocidad medida: Estimar basado en historias completadas
🎨 Estándares de codificación: Reglas consistentes para todo el equipo
🔒 Propiedad colectiva del código: Cualquiera puede modificar cualquier parte

✅ Ventajas

  • Altísima calidad de código (TDD, pair programming)
  • Reducción drástica de defectos
  • Feedback continuo del cliente
  • Alta capacidad de respuesta a cambios
  • Mejora la comunicación del equipo

❌ Desventajas

  • Requiere programadores muy disciplinados
  • Cliente debe estar 100% disponible (costoso)
  • Pair programming puede ser ineficiente para tareas simples
  • Difícil de escalar a equipos grandes
  • Menor documentación (el código es la documentación)
📌 ¿Cuándo usar XP?
• Proyectos donde la calidad del código es la máxima prioridad
• Equipo pequeño (2-10 personas) con alta disciplina
• Requisitos cambiantes y poco claros
• Cliente disponible para resolver dudas constantemente
• Proyectos de alto riesgo donde los errores son muy costosos

📐 Modelo en V (V-Model)

🎬 Modelo en V (V-Model)
                    REQUISITOS ─────────────────────────► VALIDACIÓN
                        │                                   │
                        ▼                                   ▼
                      DISEÑO ──────────────────────────► PRUEBAS SISTEMA
                        │                                   │
                        ▼                                   ▼
                 IMPLEMENTACIÓN ◄─────────────────────► PRUEBAS UNITARIAS
                (código + pruebas unitarias)

                Lado izquierdo: desarrollo         Lado derecho: pruebas

✅ Ventajas

  • Las pruebas se planifican desde el inicio
  • Relación clara entre fase de desarrollo y prueba
  • Alta trazabilidad de requisitos a pruebas
  • Bueno para sistemas críticos (seguridad, médicos)
  • Documentación exhaustiva

❌ Desventajas

  • Rígido como Cascada (no tolera cambios)
  • El cliente ve el producto hasta el final
  • Puede generar burocracia excesiva
  • Requiere mucha documentación
📌 ¿Cuándo usar el Modelo en V?
• Sistemas críticos (aeronáutica, médico, nuclear)
• Proyectos con regulaciones estrictas (DO-178C, IEC 62304)
• Requisitos estables y bien documentados
• Cuando la seguridad es prioridad máxima
• Equipos grandes que necesitan trazabilidad completa

🌀 Espiral (Spiral Model) - Basado en Riesgos

🎬 Modelo Espiral - Ingeniería de Software
🎬 Metodología tradicional - Modelo espiral
📊 Estructura del modelo espiral:

El modelo espiral combina desarrollo iterativo con gestión de riesgos. Cada vuelta (espiral) tiene 4 cuadrantes:

🎯 1. Determinar objetivos: Establecer metas, alternativas y restricciones
⚠️ 2. Evaluar riesgos: Identificar y mitigar riesgos técnicos y de gestión
🛠️ 3. Desarrollar y probar: Construir el producto o prototipo
📋 4. Planificar siguiente iteración: Revisar y planificar el siguiente ciclo

Cada iteración produce una versión más completa del software.

✅ Ventajas

  • Gestión explícita de riesgos en cada iteración
  • Alta flexibilidad para requisitos cambiantes
  • Permite prototipos evolutivos
  • Bueno para proyectos grandes y complejos
  • El cliente ve versiones tempranas
  • Escalable a proyectos de cualquier tamaño

❌ Desventajas

  • Requiere experiencia en análisis de riesgos
  • Puede ser costoso (muchas iteraciones)
  • No es adecuado para proyectos pequeños
  • Depende de buenos evaluadores de riesgo
  • Más complejo que cascada o ágil puro
📌 ¿Cuándo usar Espiral?
• Proyectos de alto riesgo (nuevas tecnologías, requisitos inciertos)
• Sistemas a gran escala y complejos
• Proyectos donde los costos de fallo son muy altos
• Cuando se necesita combinar ventajas de cascada y prototipado
• Clientes que quieren ver evoluciones pero con gestión formal

🧩 RUP (Rational Unified Process)

🎬 Metodología RUP Rational Unified Process
🎬 VIDEO 12 METODOLOGIA RUP
📊 Fases de RUP:

┌─────────────────────────────────────────────────────────────────────┐
│ INICIO → ELABORACIÓN → CONSTRUCCIÓN → TRANSICIÓN │
└─────────────────────────────────────────────────────────────────────┘

🚀 Inicio: Definir alcance, caso de negocio, análisis preliminar
📐 Elaboración: Arquitectura base, plan detallado, mitigación de riesgos
🔨 Construcción: Desarrollo incremental, pruebas, integración continua
📦 Transición: Despliegue, capacitación, liberación al cliente

✅ Ventajas

  • Muy documentado y estandarizado
  • Escalable a proyectos grandes y equipos distribuidos
  • Iterativo e incremental (como ágil pero con estructura formal)
  • Uso de UML para modelado visual
  • Gestión clara de artefactos y entregables
  • Adaptable a diferentes tipos de proyectos

❌ Desventajas

  • Puede ser burocrático y pesado para proyectos pequeños
  • Requiere mucha documentación
  • Curva de aprendizaje alta
  • Menos popular que Scrum en startups
  • Necesita herramientas específicas (Rational Rose, etc.)
📌 ¿Cuándo usar RUP?
• Proyectos empresariales grandes (bancos, seguros, gobierno)
• Equipos grandes y distribuidos geográficamente
• Proyectos que requieren trazabilidad completa y auditoría
• Cuando el cliente exige documentación formal pero quiere iteraciones
• Organizaciones que ya usan UML y herramientas IBM/Rational

📦 Lean Software Development

🎬 Qué es la metodología Lean
📊 7 principios de Lean Software Development:

1️⃣ Eliminar desperdicios: Código innecesario, esperas, defectos, cambios de prioridad
2️⃣ Ampliar aprendizaje: Iteraciones cortas, feedback continuo, documentación justa
3️⃣ Entregar rápido: Ciclos cortos, releases frecuentes, valor temprano
4️⃣ Decidir lo más tarde posible: Postergar compromisos hasta tener más información
5️⃣ Entregar rápido: Responder a cambios del mercado ágilmente
6️⃣ Respetar al equipo: Autoorganización, sin micromanagement
7️⃣ Optimizar el todo: Ver el sistema completo, no partes aisladas

✅ Ventajas

  • Reduce drásticamente tiempos de entrega
  • Mínimo desperdicio (código muerto, reuniones innecesarias)
  • Alta eficiencia y productividad
  • Empodera al equipo técnico
  • Combina bien con Kanban y DevOps
  • Excelente para entornos de alta competencia

❌ Desventajas

  • Requiere disciplina y madurez del equipo
  • Puede ser difícil de implementar en culturas tradicionales
  • Menor documentación (puede afectar a equipos grandes)
  • Depende de buena comunicación interna
  • No es adecuado para sistemas críticos con regulaciones estrictas
📌 ¿Cuándo usar Lean?
• Equipos que buscan máxima eficiencia y rapidez
• Entornos con alta competencia donde el time-to-market es crítico
• Proyectos donde el desperdicio es visible (largas esperas, mucho código no usado)
• Organizaciones que ya tienen experiencia ágil y quieren optimizar
• Startup o producto digital con iteraciones muy rápidas

🔧 Metodología de Prototipos (Prototyping)

🎬 Metodología Del Prototipado
📊 Proceso de prototipado:

┌─────────────────────────────────────────────────────────────────────┐
│ 1. REQUISITOS 2. CONSTRUIR 3. CLIENTE 4. REFINAR │
│ BÁSICOS → PROTOTIPO → PRUEBA → PROTOTIPO │
└─────────────────────────────────────────────────────────────────────┘
│
▼
┌─────────────────────────────────────────────────────────────────────┐
│ 5. DESARROLLO FINAL │
└─────────────────────────────────────────────────────────────────────┘

✅ Ventajas

  • Reduce ambigüedad de requisitos
  • Cliente ve resultados desde el inicio
  • Detecta errores temprano
  • Mejora la comunicación cliente-equipo
  • Ideal para interfaces de usuario complejas
  • Flexibilidad para cambios

❌ Desventajas

  • El cliente puede confundir prototipo con producto final
  • Puede generar expectativas poco realistas
  • Potencial de "scope creep" (más funcionalidades de las necesarias)
  • Requiere tiempo adicional para construir prototipos
  • No es adecuado para sistemas críticos sin requisitos claros
📌 ¿Cuándo usar Prototipos?
• Requisitos poco claros o ambiguos
• Cliente quiere ver resultados rápidamente
• Proyectos con interfaces de usuario complejas (UX/UI crítico)
• Productos innovadores donde no hay referencia previa
• Cuando se necesita validar ideas antes de invertir en desarrollo completo

📈 Modelo Incremental

🎬 Modelo Incremental | Desarrollo de Software
📊 Estructura incremental:

┌─────────────────────────────────────────────────────────────────────┐
│ Incremento 1 Incremento 2 Incremento 3 Incremento n │
│ (funcionalidad (añade más (añade más (producto │
│ base) funciones) funciones) completo) │
└─────────────────────────────────────────────────────────────────────┘
Cada incremento entrega una versión funcional que añade valor al cliente.

✅ Ventajas

  • Entregas parciales de valor temprano
  • El cliente puede usar funcionalidades mientras se desarrolla el resto
  • Reduce riesgo de proyecto (fallo temprano = menos pérdida)
  • Flexibilidad para ajustar prioridades entre incrementos
  • Buena para proyectos grandes que se pueden dividir
  • Feedback temprano del usuario

❌ Desventajas

  • Requiere buena planificación de incrementos
  • La arquitectura debe soportar adiciones progresivas
  • Puede derivar en "parcheo" si no se planifica bien
  • No todos los proyectos son divisibles en incrementos independientes
  • Puede haber refactorización costosa entre incrementos
📌 ¿Cuándo usar Incremental?
• Proyectos grandes que se pueden dividir en partes funcionales
• Necesidad de entregar valor rápidamente al negocio
• Recursos limitados (se puede priorizar por valor)
• Proyectos donde los requisitos cambian pero se pueden congelar por incremento
• Cuando el cliente quiere ver avances sin tener que usar metodología ágil completa
